앞 Lesson에서는 IP 패킷이 목적지까지 전달되는 큰 흐름을 봤습니다. 이번에는 그 패킷 안팎의 데이터가 계층을 지날 때 어떤 이름으로 불리고, 왜 크기를 나누는지 살펴봅니다. 이름을 줄줄 외우기보다 **어느 계층이 무엇을 다루는지** 연결하면 덜 헷갈립니다.

## 같은 데이터에 계층마다 다른 이름이 붙는다

Chrome 같은 브라우저가 사진을 보낸다고 생각해 보겠습니다. 사용자는 ‘보내기’를 한 번 누르지만, 데이터는 여러 계층의 처리를 거칩니다. TCP는 바이트 흐름(Stream)을 세그먼트(Segment)로 나누고, IP는 이를 패킷(Packet)으로 다루며, 이더넷 링크는 패킷을 프레임(Frame)에 담습니다. 프레임을 전기·빛·전파 신호로 바꾸는 물리 계층에서는 비트(bit)를 주고받습니다. 즉, **Frame은 모든 하위 계층의 이름이 아니라 이더넷 같은 링크 계층의 데이터 단위**입니다.

택배로 비유하면 큰 짐을 운반하기 알맞게 나누고, 배송 단계마다 필요한 정보를 붙여 보내는 것과 비슷합니다. 물건은 이어지지만 각 단계가 처리하는 단위와 붙이는 정보가 달라 이름도 달라집니다. 네트워크에서는 각 계층이 위 계층의 데이터를 자기 데이터 안에 담고 필요한 헤더를 붙입니다. 먼저 **TCP—Segment, IP—Packet, Ethernet—Frame**을 짝지어 기억하세요. 물리 계층은 그 프레임의 비트를 신호로 바꿉니다.

## Socket과 Stream

소켓(Socket)은 프로그램이 운영체제의 네트워크 기능을 이용해 데이터를 보내고 받는 출입구입니다. 사용자 모드(User mode)에서 실행되는 브라우저 같은 애플리케이션은 소켓에 데이터를 쓰고(write), 상대편 프로그램은 소켓에서 읽습니다(read). TCP 소켓에서 다루는 데이터는 바이트가 순서대로 이어진 흐름인 Stream입니다. 여기서 Stream은 유튜브 같은 서비스 이름이 아니라, TCP가 데이터를 연속된 바이트 흐름으로 다루는 방식을 뜻합니다.

수도꼭지를 틀면 물이 흐릅니다. 꼭지를 연 사람은 지금까지 얼마나 받았는지는 알 수 있어도, 물이 언제 얼마나 더 나올지는 미리 알기 어렵습니다. TCP의 Stream도 이처럼 전체 크기나 끝이 미리 정해지지 않은 흐름으로 다룰 수 있습니다.

그 흐름 속에서 ‘여기까지가 메시지 한 개’인지는 애플리케이션이 정합니다. 예를 들어 채팅 프로그램이 줄바꿈 문자를 메시지의 끝으로 정했다면, 프로그램은 받은 바이트에서 줄바꿈을 찾아 메시지를 나눕니다. 물은 그냥 흐르고 어디서 컵을 바꿔 들지는 사용하는 쪽이 정하는 셈입니다.

기억할 점은 프로그램이 한 번 write한 데이터가 상대편에서 같은 크기로 한 번 read되거나, TCP 세그먼트 하나로 도착한다고 보장되지 않는다는 것입니다. 받은 프로그램은 여러 번 읽은 내용을 이어 메시지를 만들 수도 있고, 한 번 읽은 바이트 안에 메시지가 여러 개 들어 있을 수도 있습니다. 메시지 경계는 애플리케이션의 규칙으로 처리해야 합니다.

## MTU는 패킷 크기, MSS는 TCP 데이터 크기의 한도다

긴 데이터를 작게 나누는 이유를 보려면 MTU와 MSS를 구별해야 합니다. MTU(Maximum Transmission Unit)는 링크에서 실어 나를 수 있는 IP 패킷의 최대 크기입니다. 흔한 이더넷 설정의 MTU 1,500바이트는 IP 헤더와 그 안의 데이터까지 합친 크기입니다. 바깥의 이더넷 헤더와 FCS까지 포함한 프레임 전체 크기가 1,500바이트라는 뜻은 아닙니다. 링크 종류와 설정에 따라 MTU는 달라질 수 있습니다.

MSS(Maximum Segment Size)는 TCP 세그먼트 하나에 실을 **TCP 데이터(payload)의 최대 크기**입니다. TCP 헤더 자체는 MSS에 포함되지 않습니다. 예를 들어 일반적인 이더넷 MTU 1,500바이트를 쓰고, IPv4 헤더와 TCP 헤더가 각각 기본 크기인 20바이트이며 옵션이 없다고 가정하면, TCP 데이터에는 1,500−20−20, 즉 최대 1,460바이트가 들어갑니다. 이 계산은 자주 만나는 조건을 보여 주는 예이지, 모든 연결의 MSS가 항상 1,460바이트라는 규칙은 아닙니다.

IPv6 기본 헤더는 IPv4 기본 헤더보다 20바이트 더 크므로, 같은 MTU와 TCP 기본 헤더를 가정하면 TCP 데이터의 예시는 1,440바이트입니다. 실제로는 TCP 옵션이나 터널링, 경로에 있는 더 작은 MTU 때문에 달라질 수 있고, TCP는 연결을 시작할 때 서로의 MSS 정보를 주고받습니다. 꼭 기억할 구별은 **MTU는 IP 패킷 전체**, **MSS는 그 안에 실릴 TCP 데이터**의 크기를 잰다는 점입니다.

4MB짜리 사진은 한 TCP 세그먼트에 담을 수 없습니다. 큰 데이터를 여러 조각으로 나눠 보내는 일을 다음 페이지에서 숫자로 따라가 봅니다.

## Stream을 Segment로 나누기

두꺼운 책을 우체국 봉투 여러 개에 나눠 보내는 모습을 떠올려 보세요. 각 봉투에는 책의 일부가 들어가고, 받는 쪽은 순서를 확인해 다시 이어 읽습니다. TCP도 소켓으로 받은 바이트 Stream을 보낼 수 있는 크기로 나누고, 각 데이터 조각에 TCP 헤더를 붙여 세그먼트(Segment)를 만듭니다. 이를 분할(Segmentation)이라고 합니다. MSS는 이때 세그먼트에 실을 TCP 데이터의 최대 크기를 가리킵니다.

계산을 쉽게 하려고 데이터가 정확히 4,000,000바이트이고, 앞에서 계산한 예시 MSS 1,460바이트를 사용할 수 있다고 가정해 보겠습니다. 1,460바이트가 꽉 찬 조각 2,739개는 모두 3,998,940바이트입니다. 남은 1,060바이트를 마지막 조각에 담으면 총 2,740개의 세그먼트가 됩니다. 마지막 조각이 더 짧은 이유는 남은 데이터만 담기 때문입니다. 실제 파일 크기와 연결 조건은 다를 수 있으므로, 이 숫자는 분할 계산을 익히기 위한 예입니다.

책 쪽수 비유는 조각을 순서에 맞춰 이어 붙인다는 점에서 유용합니다. 다만 TCP는 페이지 단위가 아니라 바이트 단위로 순서를 관리합니다. 그리고 애플리케이션이 쓴 데이터의 경계와 세그먼트의 경계가 일치한다고 약속하지 않습니다. 운영체제와 네트워크가 데이터의 크기와 상황에 맞춰 세그먼트를 구성합니다.

## TCP Segment를 IP Packet과 Ethernet Frame에 담는다

앞 Lesson에서 살펴본 캡슐화 흐름을 이번에는 크기에 초점을 맞춰 보겠습니다. IP 계층은 TCP 세그먼트에 IP 헤더를 붙여 패킷(Packet)을 만듭니다. IP 헤더에는 출발지와 목적지 IP 주소 등이 들어 있습니다. 이어 이더넷 계층은 같은 링크의 다음 장비까지 전달할 정보를 담은 이더넷 헤더와 오류 확인 정보를 붙여 프레임(Frame)을 만듭니다. 각 계층이 자기 정보를 덧붙여 감싸는 원리는 앞 Lesson에서 다뤘고, 여기서는 그 결과 각 단위의 크기가 어떻게 달라지는지 확인합니다.

숫자로 층을 따라가 보겠습니다. 이더넷 MTU가 1,500바이트이고 IPv4 기본 헤더 20바이트, TCP 기본 헤더 20바이트, TCP 데이터 1,460바이트라고 가정하면 TCP 세그먼트는 1,480바이트입니다. IP 헤더 20바이트가 붙으면 IP 패킷은 1,500바이트가 됩니다. 이더넷 프레임에는 그 패킷을 담는 이더넷 헤더 14바이트와 전송 중 오류를 확인하는 FCS(Frame Check Sequence) 4바이트가 더해져, 통상적인 이더넷 II 프레임 크기는 1,518바이트가 됩니다. 이 계산은 헤더 옵션이나 VLAN 태그가 없는 예시이며, 프레임 앞의 프리앰블과 프레임 사이 간격은 프레임 크기에 포함하지 않습니다.

따라서 ‘MTU가 1,500바이트’라고 해서 이더넷 프레임 전체가 1,500바이트인 것은 아닙니다. 이 예에서 MTU는 프레임에 실린 IP 패킷의 크기 한도이고, 프레임은 링크 계층의 헤더와 FCS까지 포함한 바깥 단위입니다. 택배로 치면 택배 상자에 담기는 내용물의 허용 크기와 포장 상자까지 포함한 전체 크기를 따로 재는 것과 같습니다. 한 문장으로 기억하면 **MTU는 IP 패킷을 재고, 이더넷 프레임은 그 패킷을 링크에 싣는 포장**입니다.

## TCP Stream과 UDP Datagram은 무엇이 다를까?

앞에서 배운 TCP는 바이트를 끊김 없는 Stream으로 다루므로, 메시지 경계를 애플리케이션이 직접 정합니다. 나중에 배울 UDP는 애플리케이션이 보낸 한 덩어리의 데이터를 하나의 데이터그램(Datagram)으로 다루며, 받는 쪽도 그 데이터그램 경계를 확인할 수 있습니다. 엽서 한 장씩 부치는 방식과 긴 두루마리 글을 이어 보내는 방식의 차이로 떠올리면 됩니다. **Datagram은 이번 단원의 암기 용어가 아니라 TCP Stream과 대비해 보는 다음 학습의 예고**입니다.

계층별로 보면 UDP 데이터그램은 IP 패킷 안에 실리고, IP 패킷은 다시 이더넷 프레임 안에 실립니다. 따라서 Datagram과 Packet은 같은 말이 아니라 서로 다른 계층의 단위입니다. 데이터그램이 경로의 MTU보다 크면 그대로 한 링크의 패킷으로 보낼 수 없으며, 실제 처리는 IP 버전과 경로 조건에 따라 달라집니다. 이 세부 처리는 IP 단편화를 배우는 Lesson에서 다시 살펴봅니다.

대화에서는 세그먼트나 데이터그램도 넓은 의미로 ‘패킷’이라고 부를 때가 있습니다. 하지만 계층별로 정확히 부를 때는 TCP의 Segment, UDP의 Datagram, IP의 Packet, 이더넷의 Frame이라고 구별합니다. 이 Lesson에서 가져갈 기본 연결은 **TCP Stream → TCP Segment → IP Packet → Ethernet Frame**입니다. UDP Datagram은 이후 UDP를 배울 때 이 흐름과 비교해 다시 익힙니다.
