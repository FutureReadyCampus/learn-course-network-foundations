## 계층마다 달라지는 데이터 이름

Chrome 같은 브라우저가 사진을 보낸다고 생각해 보겠습니다. 사용자는 ‘보내기’를 한 번 누르지만, 데이터가 네트워크를 내려가며 각 계층에서 다뤄지는 단위의 이름은 달라집니다. TCP는 세그먼트(Segment), IP는 패킷(Packet), 이더넷 같은 링크 계층은 프레임(Frame)을 다룹니다. TCP가 아니라 UDP를 쓰면 UDP 데이터그램(Datagram)이 IP 패킷 안에 들어갑니다.

택배로 비유하면 이삿짐 전체를 나눠 포장하고, 송장과 배송 정보를 붙여, 택배 차량에 실어 보내는 모습과 비슷합니다. 물건은 이어지지만 각 단계가 처리하는 단위와 붙이는 정보가 달라 이름도 달라집니다. 다만 네트워크는 물건을 다른 상자로 옮겨 담는 대신, 각 계층이 앞 단계의 데이터에 자기 헤더를 덧붙여 감쌉니다. 정확히 구별해야 할 때는 Stream, Segment, Packet, Frame이라는 이름을 계층과 짝지어 기억하세요.

## Socket과 Stream

소켓(Socket)은 프로그램이 네트워크로 데이터를 보내고 받는 출입구입니다. 사용자 모드(User mode)에서 실행되는 브라우저 같은 애플리케이션은 소켓을 통해 데이터를 주고받습니다. TCP 소켓에서 다루는 데이터는 바이트가 순서대로 이어진 흐름인 Stream입니다. 영상 스트리밍에서 ‘계속 흘러오는 데이터’라고 할 때와 비슷한 표현이지요. 프로그램은 소켓에 데이터를 쓰고(write), 상대편 프로그램은 소켓에서 읽습니다(read).

수도꼭지를 틀면 물이 흐릅니다. 꼭지를 연 사람은 지금까지 얼마나 받았는지는 알 수 있어도, 물이 언제 얼마나 더 나올지는 미리 알기 어렵습니다. TCP의 Stream도 이처럼 전체 크기나 끝이 미리 정해지지 않은 흐름으로 다룰 수 있습니다.

그 흐름 속에서 ‘여기까지가 메시지 한 개’인지는 애플리케이션이 정합니다. 예를 들어 채팅 프로그램이 줄바꿈 문자를 메시지의 끝으로 정했다면, 프로그램은 받은 바이트에서 줄바꿈을 찾아 메시지를 나눕니다. 물은 그냥 흐르고 어디서 컵을 바꿔 들지는 사용하는 쪽이 정하는 셈입니다.

기억할 점은 프로그램이 한 번 write한 데이터가 상대편에서 같은 크기로 한 번 read되거나, TCP 세그먼트 하나로 도착한다고 보장되지 않는다는 것입니다. 받은 프로그램은 여러 번 읽은 내용을 이어 메시지를 만들 수도 있고, 한 번 읽은 바이트 안에 메시지가 여러 개 들어 있을 수도 있습니다. 메시지 경계는 애플리케이션의 규칙으로 처리해야 합니다.

## MSS와 MTU

긴 데이터를 작게 나누는 이유를 보려면 MTU와 MSS를 구별해야 합니다. MTU(Maximum Transmission Unit)는 한 링크에서 IP 패킷을 보낼 때 허용되는 최대 크기입니다. 이더넷에서 흔히 쓰는 MTU 1,500바이트는 IP 패킷 크기의 예이며, 프레임의 이더넷 헤더와 FCS까지 더한 전체 크기를 뜻하지는 않습니다. 링크 종류나 설정에 따라 MTU가 달라질 수 있습니다.

MSS(Maximum Segment Size)는 TCP 세그먼트 하나에 실을 TCP 데이터의 최대 크기입니다. TCP 헤더는 MSS에 포함되지 않습니다. 예를 들어 일반적인 이더넷 MTU 1,500바이트를 쓰고, IPv4 헤더와 TCP 헤더가 각각 기본 크기인 20바이트이며 추가 헤더 옵션이 없다고 가정하면, TCP 데이터는 1,500에서 20과 20을 뺀 1,460바이트까지 들어갈 수 있습니다. 그래서 이런 조건에서 MSS를 약 1,460바이트라고 설명합니다.

이 값은 늘 1,460바이트라는 뜻이 아닙니다. IPv6 기본 헤더는 IPv4보다 20바이트 더 크므로 같은 MTU와 TCP 기본 헤더를 가정하면 TCP 데이터의 예시는 1,440바이트입니다. TCP 옵션이나 터널링, 경로의 더 작은 MTU가 있으면 실제 전송 크기는 달라질 수 있습니다. 핵심은 MTU가 IP 패킷의 크기 한도이고, MSS는 TCP 세그먼트 안에 담는 데이터의 크기 한도라는 점입니다.

4MB짜리 사진을 한 번에 하나의 TCP 세그먼트에 넣을 수는 없습니다. 큰 데이터를 여러 조각으로 나누어 보내는 이유가 바로 여기에 있습니다.

## Stream을 Segment로 나누기

두꺼운 책을 우체국 봉투에 나눠 보내는 모습을 떠올려 보세요. 봉투마다 책의 일부를 넣고, 받는 사람이 순서대로 다시 이어 읽을 수 있게 쪽수를 붙입니다. TCP도 소켓으로 전달된 바이트 Stream을 MSS에 맞는 크기의 데이터 조각들로 나누고, 각 조각에 TCP 헤더를 붙여 세그먼트(Segment)를 만듭니다. 이를 분할(Segmentation)이라고 합니다.

계산을 쉽게 하려고 데이터가 4,000,000바이트이고, 앞에서 든 조건에 따른 MSS가 1,460바이트라고 해 보겠습니다. 1,460바이트가 꽉 찬 조각 2,739개는 모두 3,998,940바이트입니다. 남은 1,060바이트를 마지막 조각에 담으면 총 2,740개의 세그먼트가 됩니다. 마지막 조각이 다른 것보다 짧아도 자연스럽습니다. 전체를 똑같은 크기로 채우는 것이 아니라, 남은 데이터만 담기 때문입니다.

책 쪽수 비유는 조각을 순서에 맞춰 이어 붙인다는 점에서 유용합니다. 다만 TCP는 페이지 단위가 아니라 바이트 단위로 순서를 관리합니다. 그리고 애플리케이션이 쓴 데이터의 경계와 세그먼트의 경계가 일치한다고 약속하지 않습니다. 운영체제와 네트워크가 데이터의 크기와 상황에 맞춰 세그먼트를 구성합니다.

## Packet과 Frame으로 보내기

세그먼트가 만들어지면 IP 계층은 IP 헤더를 붙여 패킷(Packet)을 만듭니다. IP 헤더에는 출발지와 목적지 IP 주소 등이 들어 있습니다. 이어 이더넷 계층은 같은 링크의 다음 장비까지 전달할 정보를 담은 이더넷 헤더와 FCS를 붙여 프레임(Frame)을 만듭니다. 이렇게 각 계층의 정보가 덧붙는 과정을 캡슐화(Encapsulation)라고 합니다.

숫자로 층을 따라가 보겠습니다. 이더넷 MTU가 1,500바이트이고 IPv4 기본 헤더 20바이트, TCP 기본 헤더 20바이트, TCP 데이터 1,460바이트라고 가정하면 TCP 세그먼트는 1,480바이트입니다. IP 헤더 20바이트가 붙으면 IP 패킷은 1,500바이트가 됩니다. 이더넷 프레임에는 그 패킷을 담는 이더넷 헤더 14바이트와 FCS 4바이트가 더해져, 통상적인 이더넷 II 프레임 크기는 1,518바이트가 됩니다. 이 계산은 헤더 옵션이나 VLAN 태그가 없는 예시이며, 프레임 앞의 프리앰블과 프레임 사이 간격은 프레임 크기에 포함하지 않습니다.

따라서 ‘MTU가 1,500바이트’라고 해서 이더넷 프레임 전체가 1,500바이트인 것은 아닙니다. 이 예에서 MTU는 프레임에 실린 IP 패킷의 크기 한도이고, 프레임은 링크 계층의 헤더와 FCS까지 포함한 바깥 단위입니다. 택배로 치면 내용물의 규격과 포장 상자까지 포함한 크기를 따로 재는 것과 같습니다.

## UDP Datagram과 용어 구별

Stream은 정해진 크기의 한 조각이 아니라 TCP가 바이트를 이어 전달하는 방식입니다. UDP는 이런 TCP Stream 대신, 애플리케이션이 보낸 한 덩어리의 데이터에 UDP 헤더를 붙여 데이터그램(Datagram)으로 다룹니다. 수신 애플리케이션도 데이터그램 단위로 받습니다. 엽서 한 장에 사연을 적어 부치는 것과 비슷해, 한 메시지의 경계가 보존된다는 점이 TCP Stream과 다릅니다.

계층별로 보면 UDP 데이터그램은 IP 패킷 안에 실리고, IP 패킷은 다시 이더넷 프레임 안에 실립니다. 그래서 UDP 데이터그램과 IP 패킷은 서로 비슷한 말이 아니라 서로 다른 계층의 단위입니다. 데이터그램이 경로의 MTU보다 크면 그대로 한 프레임에 실을 수 없으며, 실제 처리는 크기와 IP 버전, 경로 조건에 따라 달라집니다.

대화에서는 세그먼트나 데이터그램을 넓게 ‘패킷’이라고 부르기도 합니다. 하지만 정확히 구별할 때는 TCP의 Segment, UDP의 Datagram, IP의 Packet, 이더넷의 Frame이라고 부릅니다. 짧게 외우면 TCP는 Stream을 Segment로 나누고, IP는 이를 Packet으로 보내며, 링크 계층은 Frame으로 이웃 장비에 전달합니다. UDP는 메시지 경계를 가진 Datagram을 IP Packet에 담아 보냅니다.
