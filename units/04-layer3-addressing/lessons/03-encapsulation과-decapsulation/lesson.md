보내는 쪽에서는 계층별 정보를 덧붙여 데이터를 감싸고, 받는 쪽에서는 바깥 정보를 확인하며 안쪽 데이터를 꺼낸다. 택배 포장과 마트료시카를 떠올리며 세그먼트, 패킷, 프레임이 어떻게 안팎으로 이어지는지 살펴보자.

## 택배 포장으로 이해하기

친구에게 책 한 권을 택배로 보낸다고 해 보자. 책을 그냥 우체국 창구에 올려놓는 대신 상자에 넣고 테이프를 붙인 뒤, 겉면에 받는 사람의 이름과 주소를 적은 송장을 붙인다. 책은 크기와 모양이 제각각이지만, 상자에 넣고 송장을 붙이면 배달하는 사람에게는 ‘주소가 적힌 짐 하나’가 된다. 이제 내용물을 직접 살피지 않고도 어디로 보낼지 판단할 수 있다.

네트워크의 Encapsulation(인캡슐레이션, 캡슐화)도 보낼 데이터에 필요한 정보를 덧붙여 하나의 전송 단위로 만드는 일이다. 데이터가 택배의 책이라면, 데이터 앞에 붙는 Header(헤더)는 송장과 비슷하다. 다만 네트워크의 상자는 손에 잡히는 물체가 아니다. 0과 1로 표현된 데이터에 헤더 정보를 붙여 만든 구조다. 이 비유는 ‘내용에 정보를 더해 한 단위로 만든다’는 점을 이해하는 데 쓰고, 실제 동작과 다른 점은 뒤에서 함께 확인하자.

## Encapsulation · 단위 안에 담기

택배 상자를 받은 직원은 보통 상자를 열어 책 제목부터 확인하지 않는다. 겉면의 송장을 보고 어느 방향으로 보낼지 정한다. 바깥에서 다루는 것은 내용물 하나하나가 아니라 ‘송장이 붙은 상자’라는 단위다. 캡슐화에도 여러 정보를 하나의 덩어리로 묶어 다루기 쉽게 만드는 단위화의 의미가 있다.

여기서 포장과 보안을 혼동하지 말자. 상자를 포장했다고 해서 내용물이 암호화되어 아무도 읽을 수 없게 된 것은 아니다. 네트워크에서 헤더를 붙여 캡슐화하는 일도 그 자체로 내용을 숨기거나 암호화하지 않는다. 내용을 보호하려면 암호화 같은 별도의 기능이 필요하다.

겹겹이 들어 있는 러시아 목각 인형 마트료시카도 떠올려 보자. 큰 인형 하나를 열면 작은 인형이 나오고, 그것을 열면 더 작은 인형이 나온다. 바깥에서 보면 하나의 인형처럼 다루지만 안에는 다른 단위가 들어 있다. 네트워크에서도 안쪽의 데이터를 먼저 하나의 단위로 만들고, 그 단위에 바깥 계층의 정보를 덧붙여 감싼다. 다만 마트료시카는 처음부터 겹이 만들어져 있는 물건이고, 네트워크 데이터는 송신 과정에서 계층을 거치며 바깥쪽 정보를 차례로 붙인다는 차이가 있다.

## Frame 안의 Packet과 Segment

노트북에서 웹 서버로 ‘안녕’이라는 데이터를 보낸다고 해 보자. 먼저 전송 계층(L4)에서 TCP 헤더를 데이터 앞에 붙인다. TCP 헤더와 데이터가 합쳐져 하나의 단위가 되며, 이를 Segment(세그먼트)라고 한다. 다음으로 인터넷 계층(L3)에서 세그먼트 앞에 IP 헤더를 붙인다. IP 헤더에는 보내는 호스트와 받을 호스트의 IP 주소 같은 정보가 담기며, 헤더와 세그먼트를 합친 단위가 IP Packet(패킷)이다.

마지막으로 링크 계층(L2)에서 IP 패킷을 실을 프레임을 만든다. Ethernet 환경에서는 프레임 헤더가 앞에 붙고, 프레임 끝에는 오류를 확인하기 위한 FCS 같은 트레일러 정보도 붙는다. 이때 IP 패킷 전체가 프레임의 Payload(페이로드), 즉 프레임에 실려 가는 내용물이다. 따라서 한 계층에서 완성한 단위가 바깥 계층에서는 Payload가 될 수 있다. IP 패킷은 L3에서 완성된 단위이지만 L2에서 바라보면 프레임 안에 실리는 내용물이다.

이 흐름을 글자로 펼쳐 보면 `프레임 헤더 | IP 헤더 | TCP 헤더 | 안녕 데이터 | 프레임 트레일러`처럼 생각할 수 있다. 실제 필드와 크기는 프로토콜에 따라 달라지므로, 이 모양은 각 계층의 관계를 이해하기 위한 간단한 그림이다.

## Decapsulation · 겉에서부터 꺼내기

받는 쪽의 네트워크 인터페이스에 프레임이 도착하면 바깥에서 안쪽으로 확인한다. 먼저 링크 계층이 프레임의 정보를 살펴보고, Ethernet 프레임이라면 FCS로 전송 중 오류가 있었는지도 확인한다. 프레임 헤더와 트레일러를 처리하면 그 안에 실려 온 IP 패킷이 다음 계층으로 전달된다.

인터넷 계층은 IP 헤더를 읽어 목적지 IP 주소 등 자기 계층의 정보를 확인한 뒤, IP 패킷의 Payload인 TCP 세그먼트를 전송 계층에 넘긴다. 전송 계층은 TCP 헤더를 확인하고 그 뒤의 데이터를 꺼내 적절한 통신 상대에게 전달한다. 우체국 직원이 송장을 확인해 다음 목적지를 정하는 것처럼 각 계층은 자기 계층의 헤더를 읽는다. 링크 계층이 TCP 내용을 해석하거나 전송 계층이 프레임의 FCS를 확인하는 식은 아니다.

이처럼 바깥 정보를 처리한 뒤 안쪽 단위를 꺼내는 과정을 Decapsulation(디캡슐레이션, 역캡슐화)이라고 한다. 택배는 보통 상자를 열어야 책을 볼 수 있고, 네트워크도 바깥 계층의 정보를 처리해야 안쪽의 데이터에 도달한다.

한 가지 범위도 구분해 두자. TCP가 전달하는 데이터는 Stream(스트림), 즉 끊김 없이 이어지는 흐름처럼 다루기도 한다. 또한 모든 네트워크 통신이 OSI 5·6·7계층마다 똑같은 헤더를 하나씩 붙이는 구조는 아니다. 지금은 여기서 본 L2 프레임, L3 패킷, L4 세그먼트가 바깥에서 안쪽으로 이어지는 흐름을 먼저 익히면 된다.

## Header와 Payload의 관계 정리

보내는 쪽은 데이터를 가장 안쪽에 두고, 각 계층을 지날 때 자기 계층의 헤더를 붙여 바깥 단위로 감싼다. ‘안녕’ 데이터에 TCP 헤더를 붙이면 세그먼트가 되고, 세그먼트에 IP 헤더를 붙이면 패킷이 되며, IP 패킷을 프레임에 실으면 링크를 통해 보낼 수 있다. 이것이 Encapsulation이다.

받는 쪽은 반대 방향으로 처리한다. 프레임의 정보를 확인해 안의 IP 패킷을 꺼내고, IP 정보를 확인해 세그먼트를 꺼낸 뒤, TCP 정보를 확인해 데이터를 전달한다. 이것이 Decapsulation이다. 마트료시카처럼 보낼 때는 안쪽부터 바깥으로 감싸고, 받을 때는 바깥부터 안쪽으로 풀어 간다고 기억하면 된다.

Header와 Payload는 고정된 두 종류의 데이터가 아니라, 어느 계층에서 보느냐에 따라 달라지는 관계다. 한 계층에서 헤더와 Payload를 합쳐 완성한 단위가 바깥 계층으로 가면 통째로 Payload가 될 수 있다. 그래서 IP 패킷은 L3에서는 하나의 패킷이고, L2 프레임 안에서는 Payload다. 보낼 때는 `데이터 → 세그먼트 → 패킷 → 프레임` 순서로 감싸고, 받을 때는 `프레임 → 패킷 → 세그먼트 → 데이터` 순서로 꺼낸다는 두 방향을 함께 기억하자. 세부 필드는 각 프로토콜을 배우는 페이지에서 다시 살펴본다.
