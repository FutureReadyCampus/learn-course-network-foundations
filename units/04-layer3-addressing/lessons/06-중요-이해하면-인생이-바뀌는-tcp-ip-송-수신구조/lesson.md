## 큰 데이터를 나눠 보내는 문제

이 절은 TCP/IP 송수신의 전체 과정을 한 번에 살펴본다. 아직 배우지 않은 TCP 개념도 포함되므로, 먼저 큰 그림을 보고 TCP 학습을 마친 뒤 다시 확인하면 좋다. 프랑스 파리의 에펠탑을 택배로 보낸다고 가정해 보자. 운송 가능한 상자에 들어가도록 분해하고, 여러 상자로 나누어 운송한 다음 목적지에서 다시 조립해야 한다. 송신 측은 데이터를 전달 가능한 크기로 나누고, 수신 측은 바이트를 순서에 맞게 애플리케이션에 전달한다.

다만 실제 네트워크에서 나누는 기준을 택배 상자 크기 하나로만 생각하면 안 된다. 링크의 MTU(Maximum Transmission Unit)는 한 링크에서 운반할 수 있는 IP 패킷의 최대 크기를 가리킨다. 흔한 유선 이더넷의 MTU는 1,500바이트지만, VPN이나 다른 링크 설정에서는 값이 달라질 수 있다. TCP는 보통 MTU에서 IP와 TCP 헤더에 쓸 공간을 고려해 MSS(Maximum Segment Size)만큼의 데이터를 세그먼트에 담는다. 따라서 큰 데이터를 보내면 작은 전달 단위 여러 개로 나뉘지만, 애플리케이션이 보낸 한 번의 덩어리와 세그먼트 하나가 항상 일대일로 대응하는 것은 아니다.

## 송신 측과 수신 측의 큰 그림

PC가 액세스 스위치와 라우터를 거쳐 인터넷에 연결되고, 반대편 서버도 라우터와 스위치를 거쳐 연결된 상황을 생각해 보자. PC에서 네이버 자료실의 파일을 다운로드한다면 서버 프로세스가 파일 데이터를 보내고 PC의 브라우저가 받는다. 물류센터에서 우리 집까지 택배가 오는 것처럼 서버는 그때 송신 측, PC는 수신 측이다. 사진을 서버에 올릴 때는 방향이 바뀌므로 송신 측과 수신 측은 장비의 고정된 역할이 아니다. 예를 들어 1,400,000바이트 파일을 보내고 세그먼트 하나에 약 1,400바이트의 데이터를 담는다고 단순화하면, 대략 천 개 정도의 세그먼트가 필요하다. 이는 크기 감을 잡기 위한 예시이며 실제 개수는 MSS, 헤더, 전송 방식 등에 따라 달라진다.

이 파일은 네트워크에서 한 번에 통째로 날아가는 것이 아니다. 작은 세그먼트들이 IP 패킷에 실려 이동하고, 각 링크에서는 프레임으로 운반된다. 그 사이 TCP 연결은 데이터를 보내는 동안 이어져 있다. 이 수업에서는 그 연결이 이미 성립했다고 가정하고, 데이터가 양 끝 프로그램 사이를 어떻게 이동하는지 따라가 보자.

## 실제 송수신 주체는 프로세스

파일을 실제로 보내고 받는 주체는 PC나 서버라는 장비 자체라기보다 그 안에서 실행 중인 프로세스다. 서버의 웹 서버 프로세스가 파일을 보내고, PC의 브라우저 프로세스가 받는다. TCP는 연결 지향 프로토콜이므로 데이터를 주고받기 전에 양 끝 TCP가 연결 상태를 만든다. 전화 통화 전에 상대와 통화 경로를 여는 비유를 떠올릴 수 있지만, TCP 연결은 사람 사이의 통화 회선처럼 전용 물리 선로를 예약한다는 뜻은 아니다.

프로세스는 소켓이라는 운영체제 인터페이스를 통해 커널의 TCP 기능을 사용한다. 우체국 창구에 편지를 맡기는 것처럼, 프로그램은 소켓을 통해 커널에 데이터를 내보내 달라고 요청한다. 소켓을 콘센트나 창구에 비유할 수 있지만, 실제로는 프로그램과 커널 사이에서 통신을 다루는 소프트웨어 인터페이스다. 프로그램이 `send`를 호출하면 데이터 바이트를 소켓으로 내보내도록 요청하고, 상대 프로그램은 소켓에서 바이트를 읽는다. 네트워크 카드나 라우터가 파일을 이해하는 것은 아니다. 이들은 주소와 프로토콜 정보를 바탕으로 데이터를 전달하고, 종단의 TCP와 애플리케이션이 내용을 처리한다.

## 소켓과 입출력 버퍼

파일이나 소켓으로 입출력할 때는 메모리 공간인 버퍼가 사용된다. 요리사가 재료를 잠시 올려 두는 도마처럼, 버퍼는 다음 단계가 바로 처리하지 못한 데이터를 잠시 맡아 둔다. 파일을 읽는 프로그램 버퍼와 커널이 관리하는 소켓 송신 버퍼는 서로 다른 공간이다. 예를 들어 서버 프로그램은 `a.bmp` 파일 전체 1.4MB를 한 번에 메모리에 올릴 수도 있고, 일정한 크기로 조금씩 읽을 수도 있다. 프로그램 버퍼를 4,096바이트로 잡아 조금씩 읽는다고 가정하면 약 342번에 나누어 읽게 된다. 이는 버퍼를 채우고 보내는 횟수의 단순 예시이며, 실제 호출 횟수나 TCP 세그먼트 수가 반드시 이 숫자와 같다는 뜻은 아니다. 직소 퍼즐 조각을 몇 개씩 가져오는 그림처럼, 파일의 일부 바이트를 프로그램 메모리로 복사한다고 생각하면 된다. 원본 파일 자체가 처음부터 퍼즐 조각으로 저장되어 있다는 뜻은 아니다.

프로그램이 소켓에 데이터를 쓰면 커널의 송신 버퍼에 바이트가 쌓이고, TCP가 전송할 만큼을 처리한다. 반대편에서는 커널의 수신 소켓 버퍼에 바이트가 쌓인 뒤 애플리케이션이 읽어 간다. 버퍼는 속도가 다른 두 작업 사이에서 데이터를 잠시 맡아 두는 대기 공간과 같다. 다만 버퍼를 사용하는지 여부와 `Buffered I/O`라는 표현은 운영체제·언어·입출력 API에 따라 구체적인 의미가 달라질 수 있으므로, 여기서는 각 단계의 메모리 공간을 구분하는 데 집중하자.

## TCP가 데이터를 분할하는 과정

TCP가 제공하는 것은 메시지 상자들의 목록이 아니라 순서가 있는 바이트 스트림이다. 프로그램이 한 번 `send`를 호출했다고 해서 수신 측에서 반드시 한 번의 `receive`로 똑같은 경계가 복원되는 것은 아니다. 운영체제 TCP 스택은 송신 버퍼의 바이트를 MSS 등 전송 조건에 맞춰 하나 이상의 TCP 세그먼트로 나누거나, 여러 번의 쓰기에서 온 데이터를 함께 담을 수 있다.

예를 들어 파일의 바이트 흐름이 길게 이어져 있고 세그먼트에 500바이트씩 담긴다고 단순화해 보자. TCP는 각 세그먼트에서 첫 데이터 바이트의 순서 번호를 기록한다. 그림에 붙인 1번·2번·3번 표시는 이해를 위한 조각 이름일 뿐, 실제 TCP 헤더에 적히는 번호가 아니다. 실제 순서 번호는 바이트 위치를 나타내므로 다음 세그먼트의 번호는 앞 세그먼트 번호에 그 세그먼트의 데이터 길이를 더한 값이 된다. TCP 세그먼트가 만들어지면 IP 계층으로 내려간다.

## IP Packet으로 포장하기

IP는 TCP 세그먼트를 페이로드로 담고 IP 헤더를 붙여 IP 패킷(데이터그램)을 만든다. 택배 내용물을 상자에 넣고 목적지 정보를 적는 비유를 떠올릴 수 있다. 그 IP 패킷은 링크 계층에서 이더넷 같은 프레임의 페이로드가 된다. 택배 상자가 IP 패킷이라면 링크마다 사용하는 운송 상자나 트럭은 프레임에 비유할 수 있다.

택배가 제주도로 이동할 때 출발지의 트럭 한 대가 목적지까지 계속 가는 것은 아니다. 중간에서 운송 수단이 바뀔 수 있다. 마찬가지로 라우터는 들어온 링크 프레임을 처리한 뒤 IP 패킷을 다음 링크에 맞는 새 프레임에 담아 보낸다. IP 패킷은 경로를 따라 전달되는 단위이고, 프레임은 각 링크 구간에서 이를 운반하는 단위다. 터널링이나 단편화 같은 특수한 경우는 별도 주제이므로 여기서는 일반적인 이더넷 전달 흐름을 기준으로 본다.

## 수신 측에서 계층을 올라가기

수신 측에 도착한 프레임은 송신 측에서 출발한 프레임과 같지 않을 수 있다. 수신 장치의 링크 계층은 프레임을 처리하고 안의 IP 패킷을 위 계층에 전달한다. IP 계층은 IP 헤더를 처리한 뒤 TCP 세그먼트를 TCP에 넘긴다. TCP는 포트와 연결 정보를 확인하고, 세그먼트에 실린 데이터 바이트를 순서에 맞춰 수신 소켓의 바이트 스트림으로 제공한다.

수신자가 택배 상자를 열어 내용물을 꺼내는 것처럼, 각 계층은 자신에게 필요한 헤더를 처리하고 다음 계층에 데이터를 넘긴다. 송신에서는 애플리케이션 데이터에 TCP 헤더, IP 헤더, 링크 헤더가 차례로 붙는 캡슐화가 일어난다. 수신에서는 반대로 각 헤더를 처리하며 올라가는 디캡슐화가 일어난다. 다만 애플리케이션이 받은 바이트가 한 번의 송신 호출 경계 그대로 복원된다고 기대하면 안 된다. 파일 같은 데이터의 의미와 경계는 애플리케이션 프로토콜이 정한다.

## 수신 버퍼와 여유 공간

수신 측 TCP는 순서에 맞춰 전달할 수 있는 데이터를 커널의 수신 소켓 버퍼에 둔다. 예를 들어 브라우저가 웹 응답을 읽기 전까지 바이트가 잠시 버퍼에 쌓일 수 있다. 버퍼 용량이 64,000바이트이고 데이터 1,460바이트가 들어왔다고 단순화하면, 남은 공간은 62,540바이트다. 브라우저 프로세스가 소켓에서 데이터를 읽으면 버퍼에 여유가 생긴다. 애플리케이션은 읽은 바이트를 다시 자체 메모리 버퍼에 담아 해석하거나 파일로 저장할 수 있다.

네트워크가 수신 버퍼를 채우는 속도와 프로세스가 데이터를 읽고 처리하는 속도는 다를 수 있다. 수도꼭지에서 물이 들어오고 배수구로 나가는 싱크대처럼, 들어오는 속도가 빠르고 비우는 속도가 느리면 물이 차오른다. 이 비유에서 수신 소켓 버퍼는 싱크대에 해당하지만, TCP는 버퍼 용량과 받은 데이터 상태를 관리한다. 애플리케이션 프로세스 자체의 메모리 버퍼와 커널의 수신 소켓 버퍼를 같은 공간으로 혼동하지 말자.

## ACK와 다음 데이터 전송

TCP 순서 번호는 세그먼트의 번호표가 아니라 바이트 위치표다. 구체적인 계산을 보자. A의 초기 순서 번호가 1000이라고 가정하자. 연결을 여는 SYN도 순서 번호 공간에서 한 자리를 사용하므로, 연결이 성립한 뒤 첫 데이터 바이트는 1001부터 시작한다. A가 1001부터 1500까지 500바이트를 보내고, 이어 1501부터 2000까지 보냈다고 하자. B가 이 바이트들을 순서대로 모두 받으면 `ACK=2001`을 보낼 수 있다. 이는 “2001번 세그먼트를 보내라”는 뜻이 아니라 “2000번 바이트까지 연속해서 받았고, 다음에는 바이트 2001을 기대한다”는 뜻이다.

이 ACK는 앞의 바이트 범위를 한꺼번에 확인하는 누적 확인 응답이다. 택배 조각 비유로 말하면 “1번, 2번 상자를 각각 확인했다”보다 “여기까지 빠짐없이 도착했으니 다음은 이 위치부터 보내면 된다”는 안내에 가깝다. 페이지 애니메이션의 `ACK 3`도 이 누적 확인을 조각 번호로 단순화해 보여 준 표기이며, 실제 TCP의 ACK 번호가 세그먼트 개수를 센다는 뜻은 아니다. TCP는 데이터를 여러 세그먼트로 나누어 전송하면서도 ACK를 확인해 전달 상태를 관리한다. 애니메이션은 흐름을 눈에 띄게 보이도록 단순화한 그림이다. 실제 송신은 매번 ACK 하나를 기다리는 방식만 있는 것이 아니라 여러 바이트를 동시에 전송 중인 상태로 둘 수 있다.

## 애플리케이션이 버퍼를 비우기

수신 프로세스가 소켓 버퍼의 바이트를 읽으면 그만큼 수신 버퍼에 여유가 생긴다. TCP는 연결 상대에게 수신 윈도우(receive window)를 광고해 현재 더 받을 수 있는 공간을 알린다. 이는 “상대가 처리할 수 있을 만큼만 보내도록 알려 주는” 흐름 제어다. 택배 수령 공간을 알려 주는 비유가 도움이 되지만, 윈도우는 한 번의 세그먼트 크기나 전송 속도 자체가 아니라 수신 측이 추가로 받아 둘 수 있는 바이트 범위를 나타낸다.

송신 측은 수신 윈도우를 넘어 상대가 버퍼에 둘 수 없는 데이터를 계속 밀어 넣지 않도록 전송량을 조절한다. 네트워크가 비트를 얼마나 빨리 옮길 수 있는가와, 상대 애플리케이션이 데이터를 얼마나 빨리 읽는가는 서로 다른 문제다. 수신 윈도우는 후자를 고려하는 흐름 제어를 돕는다. 네트워크 혼잡 때문에 전송량을 조절하는 혼잡 제어와는 구별해야 한다.

## Loss와 재전송

네트워크에서는 전송 중 데이터가 유실될 수 있다. 택배가 경로에서 사라진 것처럼 세그먼트가 목적지 TCP까지 도착하지 않는 경우다. TCP 송신 측은 확인되지 않은 데이터에 대한 ACK가 오래 도착하지 않으면 재전송 타이머 만료를 근거로 데이터를 다시 보낼 수 있다. 다음 예상 바이트를 담은 ACK가 반복해서 도착하는 것도 중간에 빈 구간이 있다는 신호가 될 수 있다. 재전송은 TCP가 손실을 복구하려는 동작이지, 그 자체로 원인이 네트워크라고 확정하는 증거는 아니다.

재전송 타이머는 왕복 지연(RTT) 추정 등에 따라 조정되며, 고정된 짧은 시간을 모든 연결에 적용하는 것이 아니다. 수신 측이 이미 받은 바이트를 다시 받으면 TCP는 애플리케이션에 같은 바이트를 중복해서 전달하지 않도록 처리하고 ACK를 다시 보낸다. 중복 ACK는 대체로 수신자가 여전히 같은 다음 바이트를 기다린다는 뜻이다. ACK와 재전송이 동시에 보인다고 해서 양쪽 프로그램의 처리 시점이 엇갈린 것이 원인이라고 단정할 수는 없다. 캡처 지점, 지연, 재정렬, 실제 손실 등 여러 원인을 함께 확인해야 한다.

## Out of order · 순서가 어긋날 때

송신 측에서 바이트 1001~1500을 담은 데이터가 손실되고 1501~2000 구간이 먼저 도착했다고 하자. TCP 수신 측은 도착 순서만으로 이 후속 바이트를 애플리케이션 스트림의 앞에 붙일 수 없다. 구현과 상황에 따라 도착한 뒤쪽 바이트를 임시로 보관할 수 있지만, 애플리케이션에는 앞의 빈 구간이 채워져 순서가 이어질 때까지 연속된 바이트로 전달하지 않는다. 이를 패킷 캡처에서는 Out of order 같은 현상으로 관찰할 수 있다.

뒤쪽 데이터만 도착하면 수신 측은 다음에 기대하는 바이트가 여전히 1001이라고 알리는 ACK를 반복할 수 있다. 누락된 바이트가 재전송되어 도착하면 앞서 보관한 뒤쪽 바이트와 이어 붙여 애플리케이션에 연속 스트림으로 전달한다. 이 때문에 “TCP가 운영체제에서 순서를 보정한다”는 표현은 절반만 맞다. TCP는 순서 번호를 이용해 연속 바이트 스트림을 제공하지만, 결손을 저절로 만들어 내거나 모든 지연을 없애지는 않는다. 결손이 복구될 때까지 뒤쪽 데이터 전달이 기다릴 수 있다.

## Zero Window · 받을 공간이 없을 때

수신 윈도우는 수신 측이 더 받아 둘 수 있다고 광고하는 공간이다. 애플리케이션이 데이터를 충분히 빨리 읽지 않으면 커널의 수신 소켓 버퍼가 차고, 광고할 여유가 줄어든다. 수신 측이 윈도우 크기 0을 알리는 상태가 Zero Window다. 이는 “인터넷 전체가 멈췄다”는 뜻이 아니라, 해당 TCP 연결의 수신 측이 현재 새 데이터를 버퍼에 더 받을 공간이 없다고 알리는 것이다.

송신 측은 새 데이터를 계속 보내지 않고 윈도우가 다시 열리는지 확인하는 동작을 할 수 있다. 수신 애플리케이션이 데이터를 읽으면 버퍼 공간이 생기고, 수신 측은 갱신된 윈도우 크기를 알린다. 이런 현상을 보면 애플리케이션이 멈췄는지, 소켓을 읽는 속도가 느린지, 서버나 클라이언트 자원이 부족한지 살펴볼 수 있다. CPU 점유율이 높을 수는 있지만 Zero Window만으로 CPU가 100%라고 결론 내릴 수 없다. 송신은 파일 읽기, 프로그램 버퍼, 송신 소켓 버퍼, TCP 세그먼트화와 IP 전달을 거치고, 수신은 반대 순서로 데이터를 처리한다.

## 송수신 구조와 장애 원인 정리

다운로드의 한 흐름을 다시 떠올려 보자. 서버 프로세스가 파일 바이트를 읽어 소켓에 쓰면 커널의 TCP가 순서 번호를 붙여 세그먼트로 전송한다. IP는 이를 패킷에 담고 링크는 프레임으로 운반한다. PC의 TCP는 프레임·패킷·세그먼트 헤더를 차례로 처리해 수신 버퍼에 바이트 스트림을 만든다. 브라우저가 그 바이트를 읽고 처리하면 수신 버퍼의 공간이 다시 생긴다. 세그먼트는 전송 단위, 패킷은 IP 전달 단위, 프레임은 링크 구간 단위이며 서로 같은 이름이 아니다.

패킷 분석에서 Lost Segment, Retransmission, Out of order, Duplicate ACK, Zero Window가 보이면 각각 “어떤 바이트 구간이 확인되지 않았는가?”, “다음에 기대하는 순서 번호는 무엇인가?”, “수신 윈도우는 얼마인가?”, “캡처한 위치가 송신·수신 중 어디인가?”를 확인하면 된다. 이 표식 하나만으로 장애가 네트워크 경로 또는 애플리케이션 중 한쪽에 있다고 확정할 수는 없다. TCP가 바이트 순서와 재전송, 흐름 제어를 어떻게 연결하는지 알면 양 끝 프로그램과 중간 경로를 함께 살펴볼 단서를 얻는다. TCP를 더 배운 뒤 이 큰 흐름을 다시 보면 각 동작이 어디에 놓이는지 훨씬 분명해질 것이다.
