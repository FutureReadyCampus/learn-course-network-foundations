핵심 개념을 주제별로 정리했다.

## TCP/IP 위에서 오가는 HTTP

네트워크를 이해하려면 개별 단어와 함께 전체 구조를 살펴보아야 한다. 이 단원의 HTTP는 TCP 연결 위에서 동작하며, 소켓 수준에서는 연속된 Stream 데이터로 다룬다. 메시지의 끝은 HTTP 규칙을 해석해 알아낸다. 실제 네트워크로 보낼 때 TCP는 Stream을 세그먼트로 나누고, IP는 이를 패킷으로 감싼다. MTU가 1,500바이트인 예에서는 이 제한에 맞는 작은 단위로 전달하며, 수신 측에서 다시 이어 붙인다. 웹 수준의 설명은 이 아래 처리를 전제로 요청과 응답을 다룬다. 기본 흐름은 문서를 요청하고 서버가 문서를 응답하는 한 쌍이다.

## 웹 서비스를 이루는 큰 구성

이제 HTML과 HTTP를 개별 기술로 보던 단계에서 웹 서비스 전체 구조로 확장한다. 네트워크 관점과 백엔드 처리 관점을 함께 연결하는 설명이다. 앞서 팀 버너스리의 웹을 소개할 때 살펴본 문서와 전달 프로토콜에서 출발한다.

## HTML 문서를 요청하고 전달

웹의 기본은 HTML 문서와 이를 전달하는 HTTP다. 브라우저는 웹 클라이언트이며, 초기 역할을 문서 뷰어로 이해할 수 있다. 웹 서버에 저장된 HTML이라는 자원을 네트워크를 통해 가져와 보여 주는 것이다. 이 단원의 구성은 TCP/IP 연결 위에서 HTTP가 성립한다는 전제를 둔다. TCP에는 연결 상태가 있지만 HTTP 자체는 Stateless로 설명한다. 두 계층의 상태를 같은 것으로 보아서는 안 된다. 실제 웹 서버 앞에는 라우터 외에도 여러 장비가 배치될 수 있다. 그림은 뒤에서 이를 더하며 확장한다.

## Browser · 문서를 화면으로

주소를 입력하면 DNS로 IP를 알아내고, 그 주소에 TCP 연결을 한 뒤 HTTP 요청을 보낸다. GET으로 문서를 요청하면 서버가 응답하고, 브라우저가 받은 HTML을 화면에 표시한다. 문서 안의 링크를 클릭하면 새로운 주소에 대해 같은 요청·응답 과정이 이어진다. 이것이 초기 웹의 기본 형태다. 이후 구조를 이해하려면 화면, 자료, 처리 규칙을 구별하는 설계 관점도 함께 볼 필요가 있다.

## 문서·데이터·제어를 분리하기

소프트웨어 설계에서는 UI, 데이터·자료구조, 제어·비즈니스 로직을 분리하는 관점이 중요하다. 서로 섞여 있으면 자료구조를 바꿀 때 화면도 함께 수정하거나 그 반대의 일이 생겨 유지보수가 어려워질 수 있다. 웹에서도 문서의 내용과 화면을 꾸미는 규칙을 구별하게 된다. 논문의 모양을 바꾸기 위해 내용까지 고쳐서는 안 되는 것과 같다. HTML에 함께 적을 수도 있지만, 역할을 분리해 관리하는 방향으로 발전한다.

## CSS · 화면을 꾸미는 규칙

화면을 꾸미는 규칙을 별도로 표현하는 것이 CSS 스타일시트다. 브라우저는 HTML 외에 CSS도 요청해 문서와 표현을 결합한다. 이미지 같은 자원도 함께 사용한다. 1990년대 중반에는 Netscape Navigator 같은 브라우저가 등장한다. 정적인 문서를 보여 주는 데서 더 나아가, 문서에 움직임을 주고 상황에 따라 내용을 제어할 방법이 필요해진다.

## JavaScript · 상호작용 추가

동적인 움직임의 규칙을 스크립트로 기술해 브라우저에서 실행한다. 이 절은 이 언어의 이름이 Mocha에서 LiveScript를 거쳐 JavaScript로 바뀐 과정을 소개한다. Java와 같은 언어라는 뜻은 아니며 이름과 일부 문법의 연관을 언급하는 설명이다. 브라우저는 HTML의 텍스트와 태그를 구분하고 구문을 분석해야 한다. 단순히 문자를 출력하는 것을 넘어 태그의 의미에 맞추어 문서를 구성한다.

## 해석·렌더링·코드 실행

브라우저에는 구문을 해석하는 Parser, 화면을 만드는 Rendering Engine, JavaScript를 실행하는 엔진이 포함된다. 서버에서 HTML뿐 아니라 CSS, JPG 등의 이미지, JavaScript 코드도 HTTP 응답으로 전달한다. 브라우저는 받은 문서를 해석하고 꾸미고 코드를 실행해 상호작용하는 화면을 만든다.

## 서버에서 처리할 일이 늘어나기

GET으로 문서를 받아 표시하는 방식만으로는 사용자가 서버의 내용에 적극적으로 개입하기 어렵다. 도서관에서 자료를 받는 것처럼, 서버가 가진 콘텐츠를 보여 주는 형태에 가깝다. 아이디와 비밀번호를 입력하고 로그인 버튼을 누르는 상황처럼, 사용자의 입력을 서버에 전달하고 결과를 받아야 하는 기능이 필요해진다. 파일 업로드도 같은 방향의 예이며, 여기서는 POST를 중심으로 설명한다.

## POST와 양방향 상호작용

사용자가 아이디와 비밀번호를 입력해 로그인 버튼을 누르면 POST 요청으로 서버에 데이터가 전달되고, 서버가 그 결과를 응답한다. GET으로 자료를 받는 설명에서 나아가, 클라이언트의 입력과 서버 처리가 이어지는 양방향 상호작용을 생각할 수 있다.

## 상태를 기억해야 하는 이유

상호작용이 이어지면 이전에 무엇을 했는지 기억해야 한다. 오늘 대화의 내용을 바탕으로 내일 대화를 이어가는 것처럼, 여러 요청 사이의 문맥이 필요하다. 그러나 HTTP 자체는 Stateless다. 따라서 애플리케이션이 필요한 중간 상태를 별도로 기억해야 한다. 클라이언트에도 서버에도 관련 정보를 보관하며, 서버는 여러 사용자의 상태를 구별해야 한다.

## Cookie와 Session

클라이언트 쪽에서는 Cookie가 이러한 기억과 연결된다. 이 이 절은 쿠키를 ‘상호작용을 위한 기억의 부산물’이라는 관점으로 이해하도록 설명한다. 서버 쪽에도 사용자와 처리 상태를 기억할 공간이 필요하다. Session이라는 상태 관리 개념과 함께, 많은 자료를 보관하는 데이터베이스로 구조를 확장해 살펴본다.

## DB와 데이터 처리

웹 서버 외에 DB 서버가 등장하고, 사용자와 관련된 자료를 보관한다. 로그인 예에서는 id가 tester, pwd가 1234라는 설명용 입력이 POST로 전달된다. 서버 관점에서 이 값은 원격지 사용자 입력이다. 전달되었다는 이유만으로 신뢰해서는 안 되며 검증해야 한다. 이는 이후 Secure Coding을 이해하는 데도 중요한 관점이다. 서버는 입력된 계정에 해당하는 자료가 있는지 데이터베이스에 조회해 결과를 처리한다.

## SQL로 데이터 요청하기

데이터베이스를 RDBMS라고 가정하면 SELECT, FROM, WHERE 등의 SQL로 자료를 질의할 수 있다. 예시에서는 입력한 아이디와 비밀번호 조건에 맞는 레코드를 찾는 흐름으로 설명한다. 이 그림에서는 웹 서버가 DB를 직접 처리하는 대신 중간의 처리 서버를 거친다. 웹 서버는 자원의 송수신, DB는 자료의 보관, 중간 서버는 연산과 처리 역할을 맡는다.

## 웹 서버·WAS·DB의 분리

웹 서버가 전달받은 입력을 처리 서버에 넘기면, 처리 로직이 결과에 맞는 HTML을 만들 수 있다. 예를 들어 이름 자리가 비어 있는 문서 틀에 tester를 채워 ‘tester님 안녕하세요’라는 문서를 생성하는 식이다. 미리 저장된 내용이 그대로 전달되면 정적 문서이고, 요청과 처리 결과에 따라 만들어지면 동적 문서다. 브라우저는 서버가 생성한 문서를 받아 화면을 바꾼다. 처리 서버는 필요한 자료를 데이터베이스와 연동해 얻는다. 웹 서버·처리 서버·DB의 역할이 연결되는 구조다.

## DB 연결과 Model

ODBC나 JDBC 같은 인터페이스를 통해 데이터베이스에 접근하고 SQL 실행 결과를 받을 수 있다. 조회 조건에 맞는 사용자를 찾았다면 인사 화면을 만들고, 찾지 못했다면 다른 안내 화면을 만드는 식이다. 같은 요청 경로라도 처리 결과와 자료에 따라 생성되는 화면은 달라진다.

## Model·View·Control로 이어 보기

중간에서 처리를 담당하는 구성 요소가 WAS(Web Application Server)다. Spring이나 JSP 등을 공부할 때 이 구조를 접할 수 있다. 자료를 다루는 Model, 눈에 보이는 결과인 View, 요청과 처리 흐름을 제어하는 Control을 구별하는 관점은 MVC 아키텍처로 이어진다. 자료와 화면, 제어를 결합해 최종 응답을 만든다는 구조다. 여기까지가 기본 웹 서비스의 큰 흐름이며, 다음 여기서 실행 환경과 추가 구성 요소를 더 살펴본다.
