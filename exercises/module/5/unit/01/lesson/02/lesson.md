# 실습 1-1 · 플레이북 쓰고 알림 두 건 수동 처리

## 이번 의뢰: 대응 절차서 요청

> **오늘 들어온 일**
>
> A사 보안 팀장이 보낸 메시지입니다:
> 「Module 4에서 만든 점수 파일에는 알림이 5건 있습니다. 예를 들어 퇴사한 `dami` 의 계정으로 서버에 요청이 온 알림은 high 등급이고, IP `198.51.100.90` 의 경로 스캔(서버의 여러 주소에 차례로 요청을 보내 약점을 찾는 일) 알림은 low 등급입니다. 지금은 제가 알림을 하나씩 열어서 계정을 잠그고(그 계정으로 로그인하지 못하게 막고) 티켓을 만드는데, 사람마다 순서가 달라서 어떤 날은 티켓을 만들지 않고 넘어갑니다.
>
> 알림 종류마다 「이런 알림이 오면 이렇게 대응한다」를 문서로 먼저 정해 주세요. 그리고 지금처럼 파일을 직접 열어 고치는 방식이 얼마나 번거롭고 틀리기 쉬운지, 알림 두 건으로 직접 해 보고, 몇 군데를 고쳤는지와 어느 알림에서 실행을 멈춰야 했는지를 알려 주세요.」
> - **왜 중요한가**: <mark>같은 알림도 사람마다 다르게 처리하면 날마다 결과가 달라지고, 알림이 늘어날수록 빠뜨리는 일이 생깁니다.</mark> 절차를 먼저 정해 두어야 프로그램이 대신 실행할 수 있습니다.

## 왜 대응 절차를 미리 정해야 하는가

1. **SOAR**(Security Orchestration, Automation and Response, 쏘아: 여러 보안 도구를 서로 연결해, 정해 둔 대응 절차대로 자동으로 실행하는 것)는 알림이 난 뒤에 사람이 하던 일을 맡습니다.
2. 오늘 질문은 하나입니다. <mark>**알림이 오면 무엇을 어떤 순서로 하고, 어떤 일은 사람의 허락을 받아야 하는가?**</mark> 이 답을 적은 문서가 플레이북입니다.

## 먼저 보기 — Module 4와 Module 5는 무엇이 다른가

- **한 줄**: Module 5는 보안관제(SOC, Security Operations Center, 에스오씨: 보안 사고를 지켜보고 대응하는 센터의 업무)에서 <mark>탐지 이후 단계인 분류 · 조치 · 보고를 자동화</mark>하는 Module입니다.

- **흐름**: 로그를 읽어 Module 4가 **알림 · 점수 · 등급**을 만들고, Module 5가 그 알림을 분류 · 승인 · 조치 · 보고해 **시스템 상태 변화와 감사 기록**을 남깁니다(위 그림).

| 관점 | Module 4 이상탐지 | Module 5 자동 대응 |
|---|---|---|
| 입력 → 출력 | 로그 → 알림 · 점수 · 등급 | 알림 → 상태 변화 · 티켓 · 차단 · 감사 기록 |
| 틀렸을 때 생기는 문제 | 오탐은 분석 시간을 낭비하고, 미탐은 위협을 놓친다 | **조치 오류는 정상 계정 · IP 를 막아 서비스를 중단시킨다** |
| 사람의 역할 | 알림을 읽고 판단한다 | 승인하고, 자동 처리 밖의 건을 맡는다 |

- 오탐은 정상인데 위협으로 잘못 찾은 것, 미탐은 진짜 위협을 못 찾은 것입니다.

- **같은 사건으로 보면** `dami` (퇴사한 사람의 계정으로 서버에 요청이 온 일)는 이렇게 이어집니다.
  - Module 4: `퇴사한 계정` 규칙에 해당해 60점 · `high` 알림이 만들어집니다.
  - Module 5: 그 알림이 인시던트가 되고, 플레이북 PB-001 이 계정 잠금과 티켓 생성을 실행합니다. 액션을 실행할 때마다 감사 기록(실습 1-2에서 설명)이 한 줄 남아, 모두 두 줄이 됩니다.

## 인시던트는 무엇인가 — 알림과 무엇이 다른가

- **한 줄**: **인시던트**(incident, 인시던트)는 <mark>알림 한 건을 처리하려고 번호를 붙여 만든 「처리할 일 한 건」</mark>입니다.
  - 알림은 「이 대상이 위험해 보인다」는 신호이고, 인시던트는 그 신호를 처리하는 동안 기록을 이어 가는 단위입니다.
  - Module 5의 모든 처리는 인시던트 한 건을 기준으로 이루어집니다.

| 구분 | 알림 | 인시던트 |
|---|---|---|
| 무엇인가 | 대상이 위험해 보인다는 신호 한 건 | 그 신호를 처리하려고 만든 기록 한 건 |
| 어디서 만드나 | Module 4의 탐지 | Module 5에서 알림을 받을 때 |
| 들어 있는 정보 | 대상(`entity`) · 등급 · 점수 · 이유 | 알림의 정보 + 번호(`id`) + 처리 상태(`status`) |

- **`dami` 로 보면**: Module 4에서 「퇴사한 계정으로 요청이 왔다」는 알림이 나옵니다(`high` · 60점).
  - Module 5에서 이 알림에 `INC-001` 번호를 붙이고 처리 상태를 `탐지됨` 으로 적으면 인시던트가 됩니다.
  - 처리가 진행되면 상태가 `탐지됨` → `분류됨` → `조치됨` 으로 바뀝니다.
- **번호가 필요한 이유**: 한 인시던트에서 일어난 일을 번호 하나로 이어서 볼 수 있습니다.
  - 계정 잠금, 티켓(`"incident": "INC-001"`), 감사 기록(실습 1-2에서 설명)에 같은 번호가 들어갑니다.
  - 번호가 없으면 「이 티켓과 이 기록이 어느 알림 때문이었는지」를 나중에 알 수 없습니다.
- **현장에서도**: Microsoft Sentinel 의 자동화 설명에서도 알림과 인시던트를 따로 부릅니다(아래 1.1 의 제품 표).
- **오늘 쓰는 인시던트**: `incident_samples.json` 의 5건(`INC-001` ~ `INC-005`)입니다. 실습 1-1에서는 두 건을 손으로 처리하고, 실습 1-2에서는 프로그램이 5건을 처리합니다.

## 1.1 대응 흐름 네 단계와 실제 제품

대응은 네 단계로 나눠 생각합니다. Module 5 전체가 이 흐름을 따라갑니다.

| 단계 | 하는 일 | 이 Module에서 |
|---|---|---|
| 탐지 | 이상한 일을 찾아 알림을 낸다 | Module 4에서 만든 점수 파일 (오늘의 입력) |
| 분류 | 알림이 진짜인지, 얼마나 급한지 정하고 상태를 기록한다 | 오늘 실습 1-2 (`분류됨` 상태) |
| 조치 | 계정 잠금 · IP 차단 같은 대응을 실행한다 | 오늘은 연습용 시스템에서 흉내 내고, 계정 잠금 · 세션 종료는 Unit 2 가 만든다 |
| 보고 | 무엇을 했는지 기록하고, 필요하면 담당자에게 알린다 | 오늘 실습 1-2에서 감사 기록을 남기고, Unit 3 · 4에서 티켓 · 리포트를 만든다 |

- 오늘 PB-001 은 감사 기록만 남기고 담당자 알림은 보내지 않습니다.

보안관제 현장에서 쓰는 SOAR 제품에도 플레이북이 있습니다.

| 제품 | 플레이북은 | 만들기 · 실행 |
|---|---|---|
| Splunk SOAR(스플렁크 쏘아) | 보안 업무를 자동으로 처리하는 파이썬 프로그램이다 | 코드 없이 화면에서 단계를 이어 붙이는 편집기로도 만든다. 새 데이터가 들어오면 켜져 있는 플레이북이 실행된다 |
| Cortex XSOAR(코텍스 엑스쏘아) | 보안 처리 과정을 자동으로 실행하는 기능이다 | 분석가가 정보를 확인하거나 상급자에게 넘기는 수동 작업과, 조건에 따라 다음 작업이 정해지는 조건 작업이 있다 |
| Microsoft Sentinel(마이크로소프트 센티널) | 마이크로소프트의 자동화 서비스인 Azure Logic Apps 로 만든 처리 순서이다 | 알림이나 인시던트가 자동화 규칙을 작동시키면 자동으로 실행되고, 사람이 직접 실행할 수도 있다 |

자세한 설명은 각 제품의 문서에 있습니다.

- Splunk SOAR: https://docs.splunk.com/Documentation/SOARonprem/latest/Playbook/CreatePlaybooks
- Cortex XSOAR: https://cortex-docs.paloaltonetworks.com/r/Cortex-XSOAR/8/Cortex-XSOAR-Cloud-Documentation/What-is-a-playbook
- Microsoft Sentinel: https://learn.microsoft.com/en-us/azure/sentinel/automate-responses-with-playbooks

- 세 제품 모두 <mark>알림이 오면 실행되는 대응 절차</mark>를 플레이북이라고 부릅니다. 오늘 만드는 플레이북은 이 제품들의 플레이북을 아주 단순하게 줄인 모양입니다.
- Cortex XSOAR 에 **사람이 확인하는 작업**이 따로 있는 것에서 보듯이, 모든 대응을 자동으로 하지는 않습니다. 바로 다음 1.2 에서 볼 플레이북 4요소 가운데 「승인」이 사람이 확인하는 부분에 해당합니다.

## 1.2 플레이북 4요소와 실제로 쓰는 값

플레이북은 네 가지를 정하면 완성됩니다. 질문 네 개에 답하는 것과 같습니다.

| 요소 | 쉬운 질문 | 오늘 JSON 파일의 키 |
|---|---|---|
| **트리거**(trigger, 트리거: 대응을 시작하게 하는 일) | 어떤 규칙이 탐지되면 시작하나? | `trigger_rule` |
| **조건**(condition, 컨디션: 트리거에 맞는 것 중 대응할 것만 고르는 기준) | 그중 어떤 것만 하나? | `min_grade` (이 등급 이상) |
| **액션**(action, 액션: 실제로 하는 대응 한 가지) | 무엇을 하나? | `actions` (리스트) |
| **승인**(approval, 어프루벌: 실행하기 전에 사람의 허락을 받는 것) | 사람의 허락이 필요한가? | `approval` |

예시 하나를 문장으로 읽습니다. 플레이북 PB-001 은 <mark>「규칙 `퇴사한 계정`이 탐지되고(트리거), 등급이 high 이상이면(조건), 계정을 잠그고 티켓을 만든다(액션). 사람의 허락 없이 자동으로 한다(승인)」</mark>입니다.

액션으로 쓸 수 있는 대응은 다음과 같습니다. 오늘은 연습용 시스템에서 실행합니다. <mark>「대상」 열을 보고 알림의 대상에 맞는 액션을 고릅니다.</mark>

| 액션 | 하는 일 | 대상 | 연습용 시스템에서 일어나는 일 |
|---|---|---|---|
| 계정 잠금 | 사용자 계정으로 로그인하거나 요청하지 못하게 한다 | 사용자 | `locked_users` 에 이름이 들어간다 |
| IP 차단 | 그 IP 에서 오는 접속을 막는다 | IP | `blocked_ips` 에 IP 가 들어간다 |
| 담당자 알림 | 담당자에게 알림을 보낸다 | 사용자 · IP 모두 | `notifications` 에 알림이 들어간다 |
| 티켓 생성 | 티켓을 만들어 담당자와 진행 상황을 추적한다 | 사용자 · IP 모두 | `tickets` 에 티켓이 들어간다 |

승인은 두 값 중 하나로 씁니다.

| 값 | 뜻 | 이런 때 씁니다 |
|---|---|---|
| `자동` | 사람의 허락 없이 실행한다 | 잘못 실행해도 영향이 작고 쉽게 되돌릴 수 있을 때 |
| `담당자 승인 필요` | 담당자가 허락해야 실행한다 | 잘못 실행하면 정상 사용자의 업무가 막힐 수 있을 때 |

- 같은 액션이라도 <mark>누구에게 실행하는지에 따라 승인 값이 달라집니다.</mark> 퇴사한 사람의 계정을 잠그면 막히는 업무가 없지만, 정상 사용자가 쓰는 IP 를 차단하면 그 사람의 업무도 막힙니다.

플레이북은 `config/playbook_registry.json` 한 파일에 모아 적습니다. 한 건의 키는 다음과 같습니다.

| 키 | 뜻 | PB-001 의 값 |
|---|---|---|
| `id` | 플레이북 번호 | `"PB-001"` |
| `name` | 플레이북 이름 | `"퇴사한 계정의 서버 요청"` |
| `trigger_rule` | 트리거: 탐지된 규칙 이름 | `"퇴사한 계정"` |
| `min_grade` | 조건: 이 등급 이상(`low` · `mid` · `high`) | `"high"` |
| `actions` | 액션: 대응 이름의 리스트 | `["계정 잠금", "티켓 생성"]` |
| `approval` | 승인 | `"자동"` |
| `reason` | 이유: 왜 이렇게 정했는지 한두 문장 | `"퇴사한 사람의 계정으로 서버에 요청이 오면 …"` |

## 1.3 플레이북은 이 Module에서 어떻게 쓰이나

- **플레이북은 Module 5 내내 계속 쓰는 파일입니다.**
  - 오늘 만든 등록 파일은 다음 Unit 들도 계속 읽습니다. Unit 2 는 `계정 잠금` 을, Unit 3 은 `티켓 생성` 을 실제로 동작하게 만들고, Unit 4 는 `approval` 을 위험 점수로 판단하게 바꿉니다(시작하기의 「Module 5 전체 지도」).

- **JSON 한 건이 플레이북의 전부일까요? 아닙니다.**
  - 플레이북은 「알림이 오면 이렇게 대응한다」는 **절차**이고, JSON 한 건은 그 절차를 프로그램이 읽을 수 있게 적은 **저장 형태**입니다.
  - 절차는 알림이 올 때마다 「알림 도착 → 인시던트 생성(탐지됨) → 맞는 플레이북 찾기 → 승인 확인 → 액션을 순서대로 실행 → 감사 기록 → 상태 변경(조치됨)」 순서로 반복해서 실행됩니다. 모든 단계가 플레이북 파일의 값을 읽습니다.

- **프로그램은 플레이북의 어느 키를 언제 읽나요?**

| 키 | 읽는 때 | 하는 일 |
|---|---|---|
| `trigger_rule` · `min_grade` | 맞는 플레이북을 찾을 때 | 탐지된 규칙이 `trigger_rule` 과 같은지, 등급이 `min_grade` 이상인지 비교한다 |
| `approval` | 실행하기 직전 | `자동` 이 아니면 멈추고 승인 대기로 기록한다 |
| `actions` | 실행할 때 | 적힌 순서대로 액션을 하나씩 실행한다 |
| `id` | 기록을 남길 때 | 어느 플레이북이 한 일인지 감사 기록에 적는다 |
| `name` · `reason` | 프로그램은 읽지 않는다 | 사람이 검토하거나 감사할 때 읽는다 |

- **현업에서도 같은 방식으로 씁니다.**
  - 플레이북은 한 번 만들고 끝나지 않습니다. 운영하면서 오탐이 반복되면 조건을 고치고, 안전하다고 확인된 액션은 승인을 `자동` 으로 바꿉니다.
  - 그래서 플레이북을 코드 안에 쓰지 않고 별도 파일에 적어 두는 것이 중요합니다. 코드를 바꾸지 않고 플레이북만 고쳐 대응을 바꿀 수 있기 때문입니다.

## 실습 1-1 · 경로 스캔 플레이북과 수동 처리

**이런 상황이 있습니다**

- **지금은**: <mark>Module 4 점수 파일에는 퇴사한 계정(dami)과 경로 스캔(IP `198.51.100.90`)이 있지만, 그 알림이 오면 무엇을 할지 정해 둔 문서가 없습니다. 처리는 모두 사람이 파일을 직접 열어 고쳐서 합니다</mark>.
- **그래서 하는 것**: 플레이북 PB-003 을 직접 쓰고, 알림 두 건(INC-001 · INC-005)을 VS Code 에서 `system_state.json` 을 열어 수동 처리합니다. 승인이 필요한 건은 담당자가 허락했다고 가정합니다.
- **끝나면**: <mark>등록 파일을 읽으면 `PB-001` · `PB-002` · `PB-003` 이 나오고, `system_state.json` 에 잠긴 계정 · 차단한 IP · 티켓이 들어 있습니다.</mark>

**할 일**

1. 등록 파일을 만들고 예시 두 건을 붙여 넣은 뒤, PB-003 한 건을 추가합니다.
2. 확인 명령으로 등록 파일을 확인합니다.
3. `system_state.json` 을 열어 INC-001 과 INC-005 를 수동 처리하고 확인 명령을 칩니다.

**`config/playbook_registry.json`** — 플레이북 목록 파일입니다.

- **무엇인가**:
  - 플레이북 4요소(트리거 · 조건 · 액션 · 승인)와 이유를 한 건씩 모아 적은 파일입니다.
  - 사람이 읽는 대응 절차서이면서, 프로그램이 읽는 설정 파일입니다.
- **어디에 쓰나**:
  - 실습 1-2: 프로그램이 이 파일을 읽어 알림에 맞는 플레이북을 찾고, 적힌 `actions` 와 `approval` 대로 실행합니다.
- **지금은**: 아래에 적힌 PB-001, PB-002 두 건을 먼저 붙여 넣습니다.

<pre class="copyable"><code>[
  {

PB-003 은 위 파일의 맨 아래 `]` 앞에 한 건을 더합니다. <mark>PB-002 의 닫는 중괄호 `}` 뒤에 쉼표를 붙이고, 새 건 뒤에는 쉼표를 붙이지 않습니다.</mark> `actions` · `approval` · `reason` 은 내가 정해 씁니다.

```
  {
    "id": "PB-003",
    "name": "경로 스캔",
    "trigger_rule": "경로 스캔",
    "min_grade": "low",
    "actions": [ 내가 정한 액션 이름들 ],
    "approval": "내가 정한 승인 값",
    "reason": "내가 정한 이유 한두 문장"
  }
```

**수동 처리하는 방법** — 프로그램을 쓰지 않습니다. VS Code 에서 `system_state.json` 을 열어 아래 표대로 값을 직접 타이핑해 넣고 저장합니다.

```
고치기 전:  "locked_users": [],
고친 뒤:    "locked_users": ["dami"],
```

- 위는 INC-001 을 처리할 때 `locked_users` 줄을 고치는 예입니다. 잠긴 계정 리스트에 `"dami"` 를 적어 넣는 것이 「계정을 잠갔다」는 뜻입니다(연습용 시스템이므로 실제 계정은 바뀌지 않습니다).
- 두 건을 처리해야 하는 곳은 다음과 같습니다.

| 인시던트 | 맞는 플레이북 | 액션대로 고칠 곳 | 티켓 (`tickets` 에 넣기) |
|---|---|---|---|
| INC-001 (dami) | PB-001 (자동) | `locked_users` 에 `"dami"` 를 넣는다 | `{"id": "TCK-1", "incident": "INC-001", "target": "dami"}` |
| INC-005 (198.51.100.90) | PB-003 (내가 쓴 것) | 내가 정한 액션대로 고친다 | 윗줄과 같은 모양, 번호는 `TCK-2` |

- 리스트에 넣을 때는 `["dami"]` 처럼 대괄호 안에 쓰고, 두 개 이상이면 쉼표로 나눕니다.
- 액션에 `담당자 알림` 을 골랐다면 `notifications` 에 `"인시던트 INC-005 확인 요청"` 처럼 글자 한 줄을 넣습니다. 실습 1-2의 실행기도 이 모양으로 적습니다.
- 고친 곳이 모두 몇 군데인지 <mark>세어 둡니다.</mark> 리스트에 값 하나(이름 · IP · 티켓 한 건)를 넣은 것을 한 군데로 셉니다. 보고서 (나)에서 씁니다.

**순서**

1. **[VS Code]** 왼쪽 목록에서 `soar_response` 안의 `config` 폴더를 오른쪽 클릭 › **New File** 을 누르고, 파일 이름 `playbook_registry.json` 을 그대로 적고 Enter 를 칩니다. 이미 있으면 그 파일을 엽니다.
2. **[VS Code]** `config/playbook_registry.json` 에 위 두 건(PB-001, PB-002)을 붙여 넣고, PB-003 한 건을 추가합니다. 쉼표 위치를 확인합니다.
3. **[터미널]** 등록 파일을 확인합니다(맥북은 `python3`). <mark>`['PB-001', 'PB-002', 'PB-003']` 이 나오면</mark> 됩니다. 오류가 나면 시작하기 레슨의 「오류가 나면」 에 있는 JSON 안내를 따릅니다.
   ```bash
   python -c "import json; print([p['id'] for p in json.load(open('config/playbook_registry.json', encoding='utf-8'))])"
   ```
   - 명령 풀이: JSON 파일을 읽어 플레이북 번호만 모아 출력합니다. 쉼표나 괄호가 틀리면 여기서 오류가 납니다.
4. **[VS Code]** `system_state.json` 을 열어 위 표대로 INC-001 과 INC-005 를 처리합니다. 저장합니다.
5. **[터미널]** 수동 처리한 결과를 확인합니다. 아래 명령은 잠긴 계정 · 차단한 IP · 티켓 수를 한 줄로 보여 줍니다.
   ```bash
   python -c "import json; s = json.load(open('system_state.json', encoding='utf-8')); print(s['locked_users'], s['blocked_ips'], len(s['tickets']))"
   ```
   - 명령 풀이: 상태 파일을 읽어 잠긴 계정 리스트, 차단한 IP 리스트, 티켓 개수를 출력합니다.
   - 나오는 것: 내가 정한 액션에 따라 다릅니다. 예를 들어 IP 차단과 티켓 생성을 골랐다면 <mark>`['dami'] ['198.51.100.90'] 2`</mark> 가 나옵니다.
6. **[보고서]** `report_u1.md` 의 `## 실습 1-1` 아래를 채웁니다(보고서 파일은 「보고서 쓰기」 레슨에서 만듭니다).
   - (가) 내가 쓴 PB-003 의 액션과 승인을 적고, 5번 확인 명령의 출력을 붙여 넣어 주세요.
   - (나) [핵심 질문] 알림 두 건을 수동 처리하면서 `system_state.json` 을 직접 고친 곳이 모두 몇 군데였는지 적고, 알림이 100건이면 어떤 문제가 생길지 적어 주세요.
   - (다) [핵심 질문] PB-003 의 승인 값을 그렇게 정한 이유를 적어 주세요. 대상이 사용자 계정이 아니라 IP 라는 점과 잘못 차단했을 때의 영향을 근거로 쓰세요.

## 실습 1-1 정리

| 하려는 일 | 코드 · 말 |
|---|---|
| 플레이북 4요소 | 트리거(언제) · 조건(어떤 것만) · 액션(무엇을) · 승인(허락이 필요한가) |
| 등록 파일의 키 | `id` · `name` · `trigger_rule` · `min_grade` · `actions` · `approval` · `reason` |
| 승인 값 | `자동` · `담당자 승인 필요` |
| 액션을 고르는 기준 | 대상이 사용자 → 계정 잠금, IP → IP 차단, 둘 다 → 티켓 생성 · 담당자 알림 |
| JSON 쉼표 | 플레이북과 플레이북 사이에는 있고, 마지막 플레이북 뒤에는 없다 |
