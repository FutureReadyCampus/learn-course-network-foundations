# 오늘의 글 쓰기

## 오늘 쓸 글 고르기

오늘 글쓰기 시간은 20분입니다. 오늘 만든 통합 엔진과 정책 점검 가운데 하나를 골라 내 포트폴리오에 **세 문장 글** 한 편으로 남깁니다. 아직 포트폴리오가 없다면 [Module 3 Unit 1 시작하기 레슨의 「자기소개 두 문장으로 시작하기」 페이지](__SITE__/exercises/module/3/unit/1/lesson/1/page/4)부터 시작합니다.

핵심 실습에서 확인한 출력과 판단을 바탕으로 글감 **하나**를 골라 문제, 고른 방법과 이유, 실행 결과를 세 문장으로 기록합니다. `report_u5.md` 는 실행 출력을 보관하는 기술 기록이고, 이 글에는 문제를 알아차린 과정과 해결 방식을 씁니다.

**20분은 이렇게 나눕니다**

| 순서 | 시간 | 하는 일 |
|---|---|---|
| 1. 고르기 | 5분 | 아래 글감 하나를 고릅니다 |
| 2. 쓰기 | 10분 | `post-short` 글 틀로 세 문장을 씁니다 |
| 3. 점검·올리기 | 5분 | 공개 점검 뒤 올리고 첫 화면을 봅니다 |

**오늘의 글감 (핵심 실습)**

1. 알림 `INC-402` 하나가 실패해도 나머지 알림은 처리됐습니다. `try` / `except` 가 없었다면 어떻게 되었을까요? 오류를 받아 넘기는 방식이 감출 수 있는 문제는 무엇인가요?
2. 같은 high 등급인데 `INC-404` 는 「차단 금지」, `INC-406` 은 「승인 대기」로 갈렸습니다. 두 이유를 비교하고, 승인 게이트가 조치 실행보다 먼저 와야 하는 이유를 써 보세요.
3. 승인 게이트를 끈 로그에는 모든 결정이 「자동」으로 적혀 있었습니다. 로그에 적힌 결정만 믿으면 왜 위반을 놓치나요? 저장된 요청으로 결정을 다시 구한 방법을 내 말로 설명해 보세요.

세 문장이면 충분합니다. 막혀서 끝내지 못한 이야기도 좋은 글입니다. 어디까지 해 봤고 어디서 멈췄는지를 적어 두면, 다음에 다시 볼 때 가장 쓸모 있는 기록이 됩니다. 더 자세한 글을 쓰고 싶으면 `post-practice` 틀을 골라도 됩니다.

> **확인** — 글감 하나를 골라 그 번호를 말할 수 있으면 성공입니다. 못 고르겠으면 `report_u5.md` 의 실행 결과에서 다시 살펴보고 싶은 장면을 고릅니다.

**게시할 글 예시**

- 제목은 **저장된 요청에서 승인 결정을 다시 계산한 이유**로 쓸 수 있습니다.
- 예시 파일은 `_posts/YYYY-MM-DD-recheck-policy.md`입니다. `YYYY-MM-DD`를 작성일로 바꿉니다.
- [실습 5-2 · 정책 준수 PASS · FAIL 표](__SITE__/exercises/module/5/unit/5/lesson/4/page/3)에서 코드와 출력 위치를 찾습니다.

> 승인 게이트를 끈 실습 로그에는 모든 결정이 ‘자동’으로 저장돼 있었다. 실행이 정책에 맞았는지 확인하기 위해 저장된 요청으로 승인 결정을 다시 계산하고 실제 실행 여부와 비교했다. 세 실습 로그를 비교한 결과, 게이트를 끈 로그에서만 두 점검 항목이 FAIL로 나왔다.

위 문장은 교재의 실습 예시입니다. 내 실행에서 같은 결과를 확인했다면 내 말로 써 봅니다. 실행 결과가 다르거나 막혔다면 내 실제 출력과 다음에 확인할 내용을 적습니다.

## 글 틀로 쓰고 올리기

설치할 것은 없습니다. 저장소 `network-study-notes` 를 연 VS Code 에서 글 파일을 만들고, 터미널에서 올립니다. 글 틀을 복사하는 방법은 [Module 3 Unit 1 시작하기 레슨의 「글 틀로 글 쓰기」 페이지](__SITE__/exercises/module/3/unit/1/lesson/1/page/10)를 봅니다.

**글 틀 고르기**

| 오늘 상황 | 고를 글 틀 |
|---|---|
| 기본(세 문장 글) | `_templates/post-short.md` |
| 막혀서 끝내지 못했다 | `_templates/post-stuck.md` |
| 문제 해결 과정을 더 자세히 정리한다 | `_templates/post-practice.md` |

**올리는 순서**

1. **[VS Code]** 저장소 `network-study-notes`의 `_posts/`에 `YYYY-MM-DD-recheck-policy.md`처럼 새 파일을 만들고 `YYYY-MM-DD`를 작성일로 바꿉니다. 이미 게시한 글은 기존 주소를 유지하도록 파일명과 `date`를 그대로 두고 내용을 고칩니다.
2. 고른 글 틀을 붙여 넣고 머리말의 `title`에 한 줄 제목을, `date`에 파일명에 쓴 날짜를 적습니다. 날짜가 미래면 글이 목록에 나오지 않습니다.

<!-- checklist -->
- [ ] `_posts` 폴더에 작성일로 시작하는 이름(예: `_posts/YYYY-MM-DD-recheck-policy.md`)으로 새 글을 만들었거나, 기존 글의 파일명과 날짜를 유지했다
<!-- /checklist -->

3. 내 문제, 고른 기준과 이유, 확인한 결과를 세 문장으로 적고 저장합니다.

**코드와 실행 근거 연결하기**

1. 글에 내 실행 결과 한 줄과 그 줄로 확인한 내용을 적습니다. 예시 글의 근거는 `FAIL 이 나온 점검 2 개 · 전체 점검 12 개`입니다.
2. 코드는 `soar_response/`에 둡니다. 아래 한 줄을 복사해 글 본문에 붙이면 Pages가 내 사이트 주소에 맞게 코드 링크를 만듭니다. 다른 글감을 골랐다면 링크의 `policy_check.py`를 `soar_engine.py` 등 내 글에 해당하는 파일명으로 바꿉니다.
3. 공개해도 되는 기술 기록을 연결하려면 내 GitHub 저장소에서 `soar_response/report_u5.md`를 열고 그 주소를 붙입니다. 글을 올린 뒤 링크를 직접 열어 확인합니다.

> **확인** — VS Code 왼쪽 목록의 `_posts` 폴더 안에 오늘 글 파일이 있고, 머리말에 내 글의 제목과 작성일이 있으면 성공입니다. 없으면 오른쪽 클릭한 폴더가 `_posts` 인지 봅니다.

## 막힐 때 힌트

**오늘 Unit에서 글이 막힐 때**

고른 글감에 따라 아래 줄을 그대로 붙이고 이어 씁니다.

| 고른 글감 | 붙일 줄 | 이어 쓸 것 |
|---|---|---|
| 글감 1(오류 격리) | 단계 2 의 `INC-402` 실패 줄과 바로 아래 `INC-403` 줄 | 두 줄 사이에 ② 의 `except` 가 한 일을 한 문장으로 |
| 글감 2(게이트 순서) | 단계 2 의 `203.0.113.80` 줄과 `gaeun` 줄 | 하나는 점수를 안 보고, 하나는 점수로 정했다는 차이 |
| 글감 3(다시 구하기) | `gate_off_log.json` 의 `INC-405` 한 줄 | mid 1점 + 함께 쓰는 IP 2점 = 3점이 승인 기준과 같다는 데서 시작 |

1. 실행 결과는 출력 전체를 붙이지 않아도 됩니다. 글에서 말하는 줄 한두 개(예: `INC-402 hana → 실패 · KeyError: 'grade'`)만 코드 상자에 붙이고, 그 줄에서 무엇을 봐야 하는지 한 문장을 덧붙입니다.
2. 감출 수 있는 문제(글감 1)는 실습 5-1 아래 정답 펼침의 「자주 틀리는 곳」에서 확인합니다.
3. 막힌 이야기를 쓸 때는 `post-stuck.md` 초안에서 증상을 적는 곳에 내 출력을 그대로 붙입니다. 예를 들어 실습 5-1에서 `IndentationError: unexpected indent` 가 났다면, 그 오류와 내가 의심한 줄(① 자리 아래 미리 채운 줄)을 적고 어떻게 찾았는지 씁니다.
4. 어디서부터 쓸지 막혔다면 `report_u5.md`에서 직접 확인한 출력 한 줄을 먼저 골라 보세요. 그 출력으로 확인한 결과를 적고, 그 결과에 이르게 된 문제와 판단을 앞에 씁니다.

**AI 도우미**

코드 설명 정리, 초안 다듬기, 내 글 점검에 쓰는 프롬프트 세 가지는 [Module 3 Unit 1 시작하기 레슨의 「쓰기 질문과 AI 도우미」 페이지](__SITE__/exercises/module/3/unit/1/lesson/1/page/11)에 있습니다. AI 도우미에게 붙여 넣는 글과 코드에는 비밀키·토큰·개인정보를 넣지 않습니다.

> **확인** — 글에서 실습의 문제, 내가 선택한 방법과 이유, 실행 결과를 읽을 수 있으면 성공입니다. 결과를 설명하기 어렵다면 위 표에서 근거가 될 줄을 골라 무엇을 봤는지 한 문장으로 씁니다.

## 공개 전 점검

올리기 전에 아래를 한 줄씩 확인합니다. 자세한 점검 방법은 [Module 3 Unit 1 시작하기 레슨의 「공개 전 점검」 페이지](__SITE__/exercises/module/3/unit/1/lesson/1/page/12)에 있습니다.

1. 글과 `soar_response/` 의 파일에 `.env` 내용, API 키, 토큰이 없습니다.
2. 개인 이메일·전화번호가 없습니다.
3. 실습 속 가상의 사용자 이름(`dami` · `gaeun` 등) 말고, 실제 다른 사람의 이름이 없습니다.
4. 글 제목이 내용을 드러내고 작성일이 파일명의 날짜와 같다

**올리기** — **[터미널]** 네 줄을 모두 「문제 없음」으로 답할 수 있으면 저장소 루트에서 점검 스크립트를 돌리고 올린 뒤 작업 폴더로 돌아옵니다. 아래 명령을 한 줄씩 칩니다. 터미널이 이미 `network-study-notes` 에 있으면 `cd ..` 는 건너뜁니다.

```bash
cd ..
python check_publish.py
git add .
git commit -m "Add module 5 unit 5 post"
git push
cd soar_response
```

- 명령 풀이: `cd ..` 저장소 루트(`…/network-study-notes`)로 올라감 · `python check_publish.py` 저장소 안의 모든 파일을 점검 · `git add .` · `git commit` · `git push` 글을 담아 기록하고 깃허브로 올림 · `cd soar_response` 작업 폴더로 돌아옴
- `python check_publish.py` 출력 마지막에 `요약: 오류 0건, 주의 0건` 이 나와야 다음 줄(`git add .`)로 갑니다. `[오류]` · `[주의]` 줄이 나오면 그 줄이 가리키는 파일을 고치고 `python check_publish.py` 를 다시 돌린 뒤 올립니다.
