## 실습 5-1 정답

**터미널에 입력합니다.**

```bash
pwd

```

<h2>채운 코드 (한 예)</h2>

직접 쓰는 곳은 세 함수에 한 줄씩(① · ② · ③)입니다. 주석 줄 바로 아래가 채운 줄이고, 그 아래 줄은 미리 채워 둔 줄입니다.

① `check_employed` 안

```python
        # ① info["employed"] 가 거짓이면 (if not …)   # ← 이 주석 바로 아래 줄에 씁니다 (8칸)
        if not info["employed"]:                                 # 퇴사했으면
```

② `check_expired` 안

```python
        # ② expires_at 이 now 보다 이르거나 같으면 (<=)   # ← 이 주석 바로 아래 줄에 씁니다 (8칸)
        if expires_at <= now:                                    # 만료 시각이 지금과 같거나 지났으면
```

③ `check_dept` 안

```python
        # ③ role_dept 에서 info["role"] 의 부서를 찾아 expected_dept 에 담는다   # ← 이 주석 바로 아래 줄에 씁니다 (8칸)
        expected_dept = role_dept[info["role"]]                  # 이 역할이 속해야 하는 부서를 찾는다
```

<h2>결과</h2>

- (가) 출력은 다음과 같고, 통과는 **1개**(만료 예외 점검), 실패는 **2개**입니다.
  - 퇴사자 계정 점검은 `dami`, 부서와 역할 점검은 `junho` 가 걸렸습니다.

```
--- 단계 1: 점검 대상 - 사용자 6 명 · 예외 4 개
--- 단계 2: 점검 결과
퇴사자 계정 점검 | 실패 | ['dami']
만료 예외 점검 | 통과 | []
부서와 역할 점검 | 실패 | ['junho']
```

- (나) 만료 예외 점검이 통과인 것은 「예외 네 개 모두 만료 시각이 아직 오지 않았다」는 뜻일 뿐입니다.
  - 예외 3번은 퇴사한 dami 의 것이라, 만료 시각(2026-11-03 18:00)이 오지 않았어도 이미 필요 없는 권한입니다.
  - 만료 점검은 시각만 보고 사용자의 상태는 보지 않아서 이 문제를 잡지 못합니다.
  - 퇴사자 계정 점검(`dami` 실패)과 함께 읽어야 「dami 의 예외 3번을 지워야 한다」는 결론이 나옵니다.
- (다) 점검 코드가 알려 주는 것은 「junho 의 부서(영업)가 `finance` 역할이 속해야 하는 부서(재무)와 다르다」까지입니다.
  - 어느 쪽이 잘못됐는지는 알려 주지 못합니다. 영업으로 옮겼는데 역할을 안 바꿨을 수도 있고, 재무 업무를 계속하는데 부서 표기만 바뀐 것일 수도 있습니다.
  - 담당자는 junho 와 팀장에게 지금 하는 일을 확인하고, 부서와 역할 중 하나를 고쳐야 합니다.
  - 코드가 바로 회수하면 junho 가 하던 정산 조회가 갑자기 막혀 업무가 멈출 수 있습니다.

<h2>왜</h2>

- 점검은 사람이 눈으로 읽는 대신 같은 기준으로 반복하려고 함수로 만듭니다.
  - 점검마다 문제 리스트를 리턴하게 하면 비어 있는지만 보고 통과와 실패를 가릴 수 있고, 보고서에 대상을 그대로 적을 수 있습니다.

<h2>자주 틀리는 곳</h2>

| 틀리는 곳 | 얼마나 | 결과 |
|---|---|---|
| ② 의 부등호를 거꾸로 `>=` 로 씀 | 많음 | 오류 없이 만료 예외 점검이 실패, 번호 `[3, 6, 7, 8]` 로 나옴 |
| ① 을 비우거나 `not` 을 빼고 씀 | 있음 | 퇴사자 계정 점검에 여섯 명 모두, 또는 dami 만 빼고 다섯 명이 나옴 |
| ③ 에서 `info["role"]` 대신 `info["dept"]` 를 씀 | 있음 | `KeyError: '영업'` 으로 멈춤 |
| ① · ② · ③ 을 12칸으로 씀 | 있음 | `IndentationError` |

- 부등호를 거꾸로 쓰면 아직 만료되지 않은 예외가 모두 실패로 나옵니다. 실행하면 다음처럼 됩니다(만료 예외 점검이 실패로 나오고 예외 번호가 네 개 모두 보이면 이 실수입니다).

```
--- 단계 1: 점검 대상 - 사용자 6 명 · 예외 4 개
--- 단계 2: 점검 결과
퇴사자 계정 점검 | 실패 | ['dami']
만료 예외 점검 | 실패 | [3, 6, 7, 8]
부서와 역할 점검 | 실패 | ['junho']
```

<h2>관제에서는</h2>

- 정기 점검 도구는 어긋난 곳을 **찾는 데까지** 자동으로 하고, 회수는 사람이 계획과 승인을 거쳐 합니다.
  - 점검이 모두 통과여도 「이 기준으로는 문제가 없다」는 뜻이므로, 점검 기준이 현실과 맞는지 주기마다 다시 봅니다.

## 실습 5-2 정답

한 예입니다. 같은 뜻이면 표현이 달라도 맞습니다. 상황마다 경우(케이스)를 나누고, 각 경우를 원인 · 고칠 파일 · 어떻게 고치나요 · 고친 뒤 확인 네 줄로 적었습니다.

먼저 원인을 세 종류로 나눕니다.

| 종류 | 뜻 | 예 |
|---|---|---|
| 데이터 문제 | 사용자 · 역할 · 예외 같은 파일의 내용이 없거나 틀림, 또는 정리가 안 된 채 남아 있음 | 퇴사한 dami 의 정보가 `users.json` 에 그대로 남아 있음 |
| 규칙 문제 | 「언제 허용하고 언제 경고할지」 기준이 비었거나 현실과 안 맞음 | 접속 위치 기준 `conditions.json` |
| 사람의 일 | 입사 · 퇴사 · 부서 이동 · 업무 지원 같은 일이 생겨 지금 파일을 고쳐야 함 | 오늘 입사한 hana 를 `users.json` 에 적어야 함 |

기준을 적어 둔 곳은 네 군데입니다: `conditions.json`(시간 · 접속 위치), `alert.json`(경고할 거부율), 점검의 90일 기준, `sla.json`(처리 기한).

---

**상황 1 · 새 직원이 들어옴**

- 케이스 A. 필요한 역할이 `roles.json` 에 이미 있는 경우
  - 원인: 사람의 일입니다. hana 가 입사했는데 `users.json` 에 hana 가 아직 없어서, 요청이 「등록되지 않은 사용자」로 거부됩니다.
  - 고칠 파일: `config/users.json`
  - 어떻게 고치나요: 새로 넣습니다. `"hana": {"role": "sales", "employed": true}` 를 적습니다(`employed: true` 는 재직 중이라는 뜻). 코드로는 `assign_role` 이 같은 일을 합니다.
  - 고친 뒤 확인: 같은 요청에서 「등록되지 않은 사용자」가 사라지고, `sales` 역할의 권한만 허용되는지 봅니다.
- 케이스 B. 필요한 역할이 `roles.json` 에 없는 경우
  - 원인: 사람의 일입니다. 새 직원 hana 에게 줄 역할이 `roles.json` 에 없어서, 역할부터 새로 만들어야 합니다.
  - 고칠 파일: 먼저 `config/roles.json`, 그다음 `config/users.json`
  - 어떻게 고치나요: 새로 넣습니다. `roles.json` 에 새 역할과 그 역할의 권한 리스트(꼭 필요한 권한만)를 적고, 케이스 A 처럼 `users.json` 에 hana 를 적습니다.
  - 고친 뒤 확인: `assign_role` 이 「부여」를 리턴하고, hana 의 요청이 새 역할의 권한 안에서만 허용되는지 봅니다.

**상황 2 · 퇴사자 계정으로 요청이 계속 들어옴**

- 케이스 A. `employed` 가 이미 `false` 인 경우 (지금의 dami)
  - 원인: 데이터 문제입니다(정리가 안 됨). dami 는 퇴사했고 `employed` 도 `false` 라서 요청은 「퇴사한 계정」으로 거부됩니다. 다만 dami 정보가 `users.json` 에 남아 있어서 같은 시도가 계속 들어오고, 퇴사자 계정 점검에도 걸립니다.
  - 고칠 파일: `config/users.json`
  - 어떻게 고치나요: 지웁니다. dami 의 정보 전체를 지웁니다.
  - 고친 뒤 확인: 같은 요청이 「등록되지 않은 사용자」로 거부되고, 퇴사자 계정 점검이 통과로 바뀌는지 봅니다.
- 케이스 B. `employed` 가 아직 `true` 인 경우
  - 원인: 데이터 문제이고 가장 위험합니다. dami 는 퇴사했는데 `"employed": true`(재직 중)로 적혀 있어서, 시스템이 재직자로 보고 요청을 **허용**합니다. 퇴사한 사람이 계속 시스템을 쓰는 셈입니다.
  - 고칠 파일: `config/users.json`
  - 어떻게 고치나요: 먼저 `"employed": true` 를 `false` 로 바꾸고, 그다음 케이스 A 처럼 dami 정보를 지웁니다.
  - 고친 뒤 확인: 같은 요청이 허용에서 「퇴사한 계정」 거부로 바뀌고, dami 정보를 지운 뒤에는 「등록되지 않은 사용자」로 거부되는지 봅니다.
- 케이스 C. 퇴사자에게 아직 만료되지 않은 예외가 남아 있는 경우
  - 원인: 데이터 문제입니다(정리가 안 됨). dami 앞으로 된 예외(예: 인수인계용)가 `exceptions.json` 에 남아 있습니다. 퇴사 검사가 먼저라 요청이 허용되지는 않지만, 점검에는 계속 나옵니다.
  - 고칠 파일: `config/exceptions.json`
  - 어떻게 고치나요: 지웁니다. dami 앞으로 된 예외를 지우고, 케이스 A 처럼 `users.json` 의 dami 정보도 함께 지웁니다.
  - 고친 뒤 확인: 점검에서 dami 의 예외가 더는 나오지 않는지 봅니다.
- 생각해 볼 것: `check_permission` 은 왜 역할보다 퇴사 여부를 먼저 볼까요?
  - 순서가 바뀌면 퇴사한 사람도 역할 권한으로 허용될 수 있기 때문입니다.

**상황 3 · 다른 팀 업무를 잠시 지원함**

- 케이스 A. 기간이 정해진 지원인 경우 (seoyeon 의 월말 정산 대조)
  - 원인: 사람의 일입니다. seoyeon 의 `sales` 역할에는 정산 조회 권한(`SETTLE:QUERY`)이 없는데 이번 달만 필요해서, 지금은 「권한 없음」으로 거부됩니다.
  - 고칠 파일: `config/exceptions.json`
  - 어떻게 고치나요: 새로 넣습니다. 예외 1개를 `{"id": 6, "user": "seoyeon", "permission": "SETTLE:QUERY", "expires": "2026-11-06 18:00", "reason": "월말 정산 대조 지원"}` 처럼 적습니다. `id` 는 아직 쓰지 않은 다음 번호이고, `expires` 는 지원이 끝나는 시각입니다. 잠깐이라 역할은 바꾸지 않습니다.
  - 고친 뒤 확인: 만료 시각 전에는 「예외 6번」으로 허용되고, 만료되면 다시 「권한 없음」으로 거부되는지 봅니다.
- 케이스 B. 지원이 끝나서 예외 기간이 지난 경우
  - 원인: 데이터 문제입니다(정리가 안 됨). 만료된 예외는 판정에서 무시되어 요청은 거부되지만, 예외가 파일에 남아 있어서 만료 예외 점검에 걸립니다.
  - 고칠 파일: `config/exceptions.json`
  - 어떻게 고치나요: 지웁니다. 만료된 예외 기록을 지웁니다.
  - 고친 뒤 확인: 만료 예외 점검이 통과로 바뀌는지 봅니다.
- 케이스 C. 지원이 아니라 업무 자체가 바뀐 경우
  - 원인: 사람의 일(부서 이동)입니다. 앞으로 계속 다른 일을 하는데 예외로 풀면, 만료 때마다 같은 요청이 다시 들어와서 예외를 계속 새로 만들어야 합니다.
  - 고칠 파일: `config/users.json`
  - 어떻게 고치나요: 값을 바꿉니다. 그 사용자의 `role` 을 새 역할로 바꿉니다(코드로는 `assign_role`).
  - 고친 뒤 확인: 새 역할의 권한으로 허용되고, 이전 역할의 권한은 더 이상 허용되지 않는지 봅니다.

**상황 4 · 새 권한이 필요함**

- 케이스 A. 정상적인 요청 (junho 의 영업 실적 정정)
  - 원인: 규칙 문제입니다. 권한을 달라는 요청을 처리하는 순서(절차)를 정해 둔 기준이 비어 있습니다. junho 가 `SALES:CHANGE` 를 달라는데 누가 승인하고 언제까지 처리할지 정해져 있지 않습니다. 담당자가 파일을 직접 고치면 누가 언제 왜 승인했는지 기록이 남지 않습니다.
  - 고칠 파일: 새로 만드는 `req_create.py`(요청서 만들기) · `req_review.py`(승인하기) · `req_grant.py`(부여하기)
  - 어떻게 고치나요: 새로 넣습니다. 절차를 코드로 만듭니다. `create_request` 로 요청서를 만들고, 검토하는 사람이 `approve_request` 로 승인하고, 승인된 것만 `grant_request` 로 부여합니다(부여하면 예외 리스트에 새 예외가 추가됩니다).
  - 고친 뒤 확인: 요청서의 `status` 가 `reviewing` → `approved` → `granted` 로 바뀌고, junho 의 `SALES:CHANGE` 요청이 예외로 허용되는지 봅니다.
- 케이스 B. 요청한 사람이 자기 요청을 승인하려는 경우
  - 원인: 사람의 일입니다. 규칙은 이미 있고 코드가 막고 있는데, 사람이 절차를 건너뛰려 한 것입니다. 요청한 사람이 스스로 승인하면 검토하는 의미가 없어서, `approve_request` 는 요청한 사람과 승인하는 사람이 같으면 승인하지 않습니다.
  - 고칠 파일: 없습니다.
  - 어떻게 고치나요: 다른 사람이 승인하도록 합니다.
  - 고친 뒤 확인: 본인이 승인하면 「본인 요청은 처리할 수 없음」이 나오고, 다른 사람이 승인하면 「승인」이 나오는지 봅니다.
- 케이스 C. 요청이 오래 처리되지 않는 경우
  - 원인: 사람의 일입니다. 검토하는 사람이 처리를 미뤄서 요청서가 처리 기한(`config/sla.json` 의 4시간)을 넘겼습니다. 4시간이 현실과 맞지 않는 것이라면 규칙 문제입니다. 기한을 넘기면 요청한 사람이 계속 기다리게 됩니다.
  - 고칠 파일: 기한이 현실에 맞지 않을 때만 `config/sla.json`
  - 어떻게 고치나요: 먼저 `check_sla_breach` 로 기한을 넘긴 요청서를 찾아 담당자에게 알립니다. 4시간이 현실에 맞지 않으면 `hours` 의 값을 바꿉니다.
  - 고친 뒤 확인: 접수한 지 6시간이 지난 검토 중 요청서가 기한을 넘긴 요청서 리스트에 나오는지 봅니다.

**상황 5 · 안 쓰는 권한이 쌓임**

- 케이스 A. 오래 안 썼고 정말 필요 없는 권한 (junho 의 `SALES:QUERY`, 91일째 안 씀)
  - 원인: 데이터 문제입니다(정리가 안 됨). 안 쓰는 권한이 남아 있습니다. 점검은 마지막으로 쓴 지 90일이 넘은 권한을 회수 후보로 뽑는데, 이 권한은 91일째라 걸렸습니다. 점검이 없으면 한 번 준 권한이 계속 남습니다.
  - 고칠 파일: 점검 코드는 `review_unused.py`, 마지막 사용 시각은 `config/access_log.json`
  - 어떻게 고치나요: 후보로 뽑힌 권한을 회수 대상으로 넘깁니다. 실제 회수는 상황 6에서 합니다.
  - 고친 뒤 확인: 점검을 다시 돌리면 후보에 나옵니다. 정확히 90일째 안 쓴 junho 의 `SETTLE:QUERY` 는 후보가 아닙니다. 기준이 「90일을 넘으면」이기 때문입니다.
- 케이스 B. 평소에 안 써도 필요한 권한 (seoyeon 의 `SALES:CHANGE`, 120일째 안 씀)
  - 원인: 사람의 일입니다. 하는 일 때문에 쓰는 때가 드문 권한입니다. seoyeon 은 6월 말과 12월 말 결산(반년 동안의 돈 계산을 마무리하는 일) 때만 씁니다. 120일 안 써서 점검에는 걸리지만, 회수하면 결산 때 일을 못 합니다.
  - 고칠 파일: `config/exclude_list.json`
  - 어떻게 고치나요: 새로 넣습니다. 사용자, 권한, 제외하는 이유를 적습니다. 이유를 적어 두어야 나중에 왜 제외했는지 알 수 있습니다.
  - 고친 뒤 확인: 이 권한이 회수 대상에서 빠지고 회수 제외로 나뉘는지 봅니다.
- 케이스 C. 사용 이력이 아예 없는 권한 (gaeun 의 `ACCOUNT:CHANGE`)
  - 원인: 케이스 B 처럼 사람의 일입니다. 계정에 사고가 났을 때만 쓰는 권한이라 평소에는 기록이 남지 않습니다. 점검은 기록이 없는 권한도 안 쓴 권한으로 뽑습니다.
  - 고칠 파일: `config/exclude_list.json`
  - 어떻게 고치나요: 케이스 B 처럼 새로 넣습니다. 이유에 「계정에 사고가 났을 때만 쓰는 권한」이라고 적습니다.
  - 고친 뒤 확인: 케이스 B 와 같습니다.
- 케이스 D. 제외 리스트에 있어도 사용자가 퇴사한 경우 (dami 의 `SALES:QUERY`)
  - 원인: 데이터 문제입니다(정리가 안 됨). 퇴사한 dami 의 정보가 제외 리스트에 남아 있습니다. 퇴사한 사람의 권한은 제외 리스트에 있어도 제외하지 않습니다. 이 권한은 「일을 넘겨받을 사람이 정해질 때까지 필요」라는 이유로 제외 리스트에 있지만, dami 가 퇴사해서 코드가 회수 대상으로 둡니다.
  - 고칠 파일: 없습니다. 코드가 이미 처리합니다.
  - 어떻게 고치나요: 회수 대상으로 둡니다. 필요하면 제외 리스트의 dami 정보를 지웁니다.
  - 고친 뒤 확인: 이 권한이 회수 제외가 아니라 회수 대상으로 나오는지 봅니다.

**상황 6 · 민감한 권한을 회수해야 함**

수업에서는 프로그램 안의 데이터를 바꾸고 회수 이력 파일(`revocation_log.json`)만 저장합니다. 실제 서비스에서는 아래 파일을 직접 고칩니다.

- 케이스 A. 예외로 받은 권한을 회수하는 경우 (seoyeon 의 정산 조회, 예외 1번)
  - 원인: 데이터 문제입니다(정리가 안 됨). 지원이 끝났는데 그 예외가 남아 있습니다.
  - 고칠 파일: `config/exceptions.json`
  - 어떻게 고치나요: 지웁니다. 그 예외 기록을 지웁니다. 영향받는 권한이 1개이고 쓰기 권한이 아니라서, 승인 없이 실행해도 됩니다.
  - 고친 뒤 확인: 회수 전과 후의 판정을 비교하면 이미 거부였던 요청은 「그대로」입니다. 이력에는 「실행」으로 남습니다.
- 케이스 B. 퇴사자의 역할을 비우는 경우 (dami 의 `sales` 역할)
  - 원인: 데이터 문제입니다(정리가 안 됨). 퇴사한 dami 에게 `sales` 역할이 남아 있습니다. 비우면 그 역할로 받던 권한 2개가 한꺼번에 사라져서 영향이 큽니다.
  - 고칠 파일: `config/users.json`
  - 어떻게 고치나요: 값을 바꿉니다. dami 의 역할을 비웁니다. 영향이 2개라서 보안 책임자의 승인을 먼저 받습니다.
  - 고친 뒤 확인: 승인 상태가 「승인됨」이면 실행되고 이력에 남는지 봅니다.
- 케이스 C. 쓰기 권한을 회수하는데 승인이 아직 없는 경우 (junho 의 `SALES:CHANGE`, 예외 2번)
  - 원인: 사람의 일입니다. 보안 책임자의 승인이라는 사람의 판단이 아직 없습니다. 쓰기 권한(`CHANGE`)을 잘못 없애면 일하던 사람이 데이터를 바꾸지 못합니다. 그래서 민감한 권한 리스트(`sensitive.json`)에 있는 권한은 보안 책임자의 승인이 있어야 회수합니다.
  - 고칠 파일: 파일을 고치지 않습니다. 승인 상태를 정하는 `revoke_approve.py` 의 결과를 봅니다.
  - 어떻게 고치나요: 승인이 아직 없으면 실행하지 않고 「승인 대기」로 둡니다.
  - 고친 뒤 확인: 이력에 「대기」로 남고, 승인이 나면 실행되는지 봅니다.
- 케이스 D. 재직 중인 사용자의 역할에서 권한을 빼는 경우 (junho 의 `SALES:QUERY`, `finance` 역할)
  - 원인: 데이터 문제입니다. `roles.json` 의 `finance` 역할이 필요한 것보다 많은 권한을 갖고 있습니다.
  - 고칠 파일: `config/roles.json`
  - 어떻게 고치나요: 지웁니다. `finance` 역할의 권한 리스트에서 그 권한을 뺍니다. `finance` 역할을 가진 모든 사용자에게 적용되므로, 먼저 사용자가 몇 명인지 확인합니다.
  - 고친 뒤 확인: junho 의 `SALES:QUERY` 판정이 허용에서 거부(권한 없음)로 바뀌는지 봅니다.
- 케이스 E. 보안 책임자가 승인을 거절한 경우
  - 원인: 사람의 일입니다. 사람이 「승인」이 아닌 결정을 내렸습니다. 코드는 결정이 「승인」일 때만 「승인됨」으로 적고, 거절이거나 결정이 없으면 모두 「승인 대기」로 둡니다.
  - 고칠 파일: 없습니다. 결정을 담은 딕셔너리(`DECISIONS`)만 확인합니다.
  - 어떻게 고치나요: 거절된 계획은 실행하지 않고 대기로 둡니다. 다시 회수하려면 거절 이유를 해결한 뒤 승인을 새로 받습니다.
  - 고친 뒤 확인: 이력에 「대기」로 남고 권한은 그대로 유지되는지 봅니다.

**상황 7 · 새벽 외부 접속, 그리고 정상 직원이 계속 거부됨**

- 케이스 A. 새벽에 밖에서 보낸 요청이 허용되는 경우
  - 원인: 규칙 문제입니다. 조건 파일에서 `SALES:CHANGE`(데이터를 바꾸는 권한) 줄이 빠져 있었다고 가정합니다(위 3.1 의 파일에는 이 줄이 이미 들어 있습니다). 기준이 없는 권한은 시간과 접속 위치를 확인하지 않아서, 밤 22시에 밖(`external`)에서 보낸 요청도 역할만 맞으면 허용됩니다.
  - 고칠 파일: `config/conditions.json`
  - 어떻게 고치나요: 빠진 줄을 새로 넣습니다. `{"permission": "SALES:CHANGE", "hours": [9, 18], "networks": ["office", "vpn"]}` 를 적습니다. 뜻은 「9시부터 18시 전까지, 사내망(`office`)이나 VPN 에서만 허용한다」입니다.
  - 고친 뒤 확인: 같은 요청(밖, 22시)이 「업무 시간 밖」으로 거부되는지 봅니다.
- 케이스 B. 정상 직원이 계속 거부되는 경우 (gaeun 이 VPN 으로 계정 변경)
  - 원인: 규칙 문제입니다. 규칙이 현실과 맞지 않습니다. gaeun 은 VPN(밖에서 회사망으로 안전하게 들어오는 연결)으로 일하는데, `ACCOUNT:CHANGE` 는 접속 위치가 `["office"]`(사내망)뿐이라서 VPN 요청이 「허용되지 않은 접속 위치」로 계속 거부됩니다.
  - 고칠 파일: `config/conditions.json`
  - 어떻게 고치나요: 값을 바꿉니다. 접속 위치 `["office"]` 를 `["office", "vpn"]` 으로 고칩니다. `external`(밖)은 넣지 않습니다. 넣으면 계정을 훔친 사람이 밖에서 보낸 요청도 허용되어 위험합니다.
  - 고친 뒤 확인: gaeun 의 VPN 요청이 허용으로 바뀌는지 봅니다. 규칙을 풀었으니 다른 요청이 같이 허용되지 않는지도 봅니다.
- 케이스 C. 업무 시간 끝 시각 정각의 요청이 거부되는 경우 (seoyeon 의 18시 정각 요청)
  - 원인: 규칙 문제입니다. 끝 시각을 포함하지 않는 약속 때문입니다. 시간대 `[9, 18]` 은 「9시 이상 18시 미만」이라서 18시 정각은 업무 시간이 아닙니다. 18시 이후에도 일하는 부서라면 규칙이 현실과 맞지 않는 것입니다.
  - 고칠 파일: `config/conditions.json`
  - 어떻게 고치나요: 값을 바꿉니다. `SALES:CHANGE` 의 `"hours": [9, 18]` 을 `[9, 20]` 으로 고칩니다. 늘린 시간에는 쓰기 요청이 모두 허용되므로, 정말 필요한 업무인지 확인한 뒤에 고칩니다.
  - 고친 뒤 확인: 18시 정각 요청이 허용되고, 20시 정각 요청은 여전히 「업무 시간 밖」으로 거부되는지 봅니다.
- 케이스 D. 조건이 없는 권한이 밖에서도 허용되는 경우 (seoyeon 의 `SALES:QUERY`, 밖 22시)
  - 원인: 규칙 문제인지 따져 볼 일이고, 지금 규칙대로라면 문제가 아닙니다. `SALES:QUERY` 는 조회만 하는 권한이라 `conditions.json` 에 조건을 걸지 않았습니다. 조건이 없는 권한은 시간과 접속 위치를 보지 않고 역할 판정 결과를 그대로 따릅니다.
  - 고칠 파일: 없습니다.
  - 어떻게 고치나요: 조회 권한에도 조건이 필요하다고 판단하면 케이스 A 처럼 `conditions.json` 에 새로 넣습니다. 필요 없다고 판단하면 그대로 둡니다.
  - 고친 뒤 확인: 조건을 넣은 경우에만 같은 요청이 거부로 바뀌는지 봅니다.
- 생각해 볼 것: 규칙을 풀면 정상 직원의 불편은 줄지만 위험한 접속도 같이 허용될 수 있습니다. 고치기 전에 무엇을 확인하면 좋을까요?

**상황 8 · 매주 어긋남을 확인해야 함**

- 케이스 A. 사람이 눈으로 확인하는 경우
  - 원인: 규칙 문제입니다. 매주 같은 기준으로 확인하는 방법이 비어 있습니다. 눈으로 세면 사람마다 기준이 다르고 오래 걸립니다. 지난주와 같은 기준으로 봤는지도 알 수 없습니다.
  - 고칠 파일: 새로 만드는 `checklist.py`(점검) · `log_summary.py`(로그 집계) · `weekly_report.py`(보고서)
  - 어떻게 고치나요: 새로 넣습니다. 점검 세 가지, 로그 집계, 주간 보고서를 코드로 만들어 같은 기준으로 한 번에 돌립니다.
  - 고친 뒤 확인: 보고서 4절에 조치가 필요한 것이 나오고, 지난주와 같은 기준으로 비교할 수 있는지 봅니다.
- 케이스 B. 경고 기준이 현실과 맞지 않는 경우
  - 원인: 규칙 문제입니다. 거부율이 `alert.json` 의 `deny_rate_limit` 이상이면 경고를 띄웁니다. 기준이 너무 낮으면 경고가 매주 떠서 아무도 보지 않게 되고, 너무 높으면 위험을 놓칩니다.
  - 고칠 파일: `config/alert.json`
  - 어떻게 고치나요: 값을 바꿉니다. `deny_rate_limit` 의 값을 바꾸고, 바꾼 이유도 기록합니다.
  - 고친 뒤 확인: 같은 로그의 거부율 40% 는 기준이 30% 이면 경고이고, 기준을 50% 로 올리면 경고 없음으로 바뀝니다. 거부된 요청 수는 그대로이므로 안전해진 것이 아니라 기준이 바뀐 것입니다.
- 케이스 C. 로그가 비어 있는 경우
  - 원인: 데이터 문제입니다. 있어야 할 로그가 모이지 않았습니다. 서버가 멈췄거나 로그를 모으지 못했을 수 있습니다. 요청이 0개면 거부율을 0% 로 계산해서, 보고서만 보면 안전해 보입니다.
  - 고칠 파일: 서버와 로그 파일 수집을 확인합니다.
  - 어떻게 고치나요: 보고서 1절의 전체 요청 수가 0개인지 먼저 봅니다. 거부율 0% 만 보고 안전하다고 판단하지 않습니다.
  - 고친 뒤 확인: 수집이 복구되면 요청 수가 다시 보이는지 봅니다.

- (가) 한 예: 데이터를 고친 상황은 1, 2, 3, 5, 6이고, 규칙을 고친 상황은 7과 8(케이스 B)입니다. 4는 요청 절차를 새로 만든 상황입니다. 규칙을 고치는 쪽이 위험이 더 큽니다.
  - 데이터를 잘못 고치면 한 사람의 권한 안에서 끝납니다.
  - 규칙을 잘못 풀면 그 규칙에 해당하는 모든 요청이 한꺼번에 영향을 받아, 위험한 접속도 같이 허용될 수 있습니다.
  - 그래서 규칙은 고치기 전에 과거 로그로 영향을 확인하는 것이 좋습니다.
- (나) 사람마다 다릅니다. 헷갈린 로직과, 읽고 쓰면서 이해한 방법(내 파일을 열어 보기, 출력을 비교하기 등)을 적으면 맞습니다.
- (다) 한 예: 보고서 문자열이나 요청 리스트를 LLM 호출에 넘겨 요약하거나, 경고가 나오면 알림으로 보내는 곳에 이을 수 있습니다.

<h2>왜</h2>

- 상황이 생겼을 때 「원인 → 고칠 곳 → 방법 → 확인」 순서로 생각하는 습관을 만들기 위해서입니다.
  - 데이터를 고치는 일과 규칙을 고치는 일은 영향 범위가 다릅니다.

<h2>자주 틀리는 곳</h2>

- 원인을 정하지 않고 바로 파일을 고치는 경우가 많습니다. 예를 들어 gaeun 이 거부되었을 때 사용자 정보부터 고치면 해결되지 않습니다. 거부 이유가 「허용되지 않은 접속 위치」이면 고칠 곳은 `conditions.json` 입니다.
- 고친 뒤 확인을 빼먹으면, 고쳤다고 생각했지만 다른 요청이 같이 허용되는 것을 놓칩니다.

<h2>관제에서는</h2>

- 인수인계 문서는 이 틀(원인 → 고칠 파일 → 방법 → 확인)로 상황별 대응을 적어 둡니다.
  - 새 담당자는 코드를 처음부터 읽지 않고, 상황에서 시작해 파일을 찾아갑니다.

<h2>결과</h2>

- (가) `apply5-1_run.py` 의 출력은 다음과 같고, 허용 **24**, 거부 **16**, 거부율 **40%** 입니다.
  - 거부 사유 중 가장 많은 것은 `허용되지 않은 접속 위치`(5개)입니다.

```
--- 단계 1: 집계 - 요청 40 건
허용 24 · 거부 16 · 거부율 40%
--- 단계 2: 거부 사유별
역할이 없음 3
업무 시간 밖 4
퇴사한 계정 4
허용되지 않은 접속 위치 5
--- 단계 3: 경고 기준
거부율 40% >= 기준 30% -> 경고
거부 4 번 이상 사용자: ['dami', 'gaeun']
```

  - `weekly_run.py` 를 다시 실행한 보고서는 「주간 보고서 생성 준비」 레슨의 실행 결과와 같습니다. 거부율 40% 는 경고 기준 30% 이상이라 **경고**이고, 실패한 점검은 퇴사자 계정 점검과 부서와 역할 점검입니다.
  - 다르게 나오면 내가 쓴 `log_summary.py` 의 함수가 완성본과 다르게 센 것입니다. 바로 위 `apply5-1_run.py` 의 출력부터 맞춰 봅니다.

- (나) 두 사람의 요청은 다음과 같이 다릅니다.
  - dami 는 4번 모두 `퇴사한 계정` 으로 거부됐고, 접속 위치가 `office` · `vpn` · `external` 로 바뀝니다. 퇴사한 사람의 계정이 정리되지 않고 남아 있어 누군가 계속 시도하고 있다는 신호입니다.
    - 먼저 퇴사자 계정 점검 결과(dami 실패)를 근거로 남은 계정을 정리하고, 누가 어디서 시도했는지 조사해야 합니다.
  - gaeun 은 5번 거부됐지만 사유가 `허용되지 않은 접속 위치` 4번과 `업무 시간 밖` 1번이고, 사내망(`office`)에서는 3번 모두 허용됐습니다.
    - 계정 관리 권한(`ACCOUNT:CHANGE`)을 사내망에서만 허용하는 규칙에 VPN · 외부 접속이 걸린 것일 수 있습니다.
    - 먼저 gaeun 에게 재택이나 외근 중이었는지 확인하고, 규칙이 실제 일하는 방식과 맞는지 검토해야 합니다.
  - dami 는 계정 차단과 조사, gaeun 은 확인과 규칙 검토가 먼저라서 같은 조치를 하면 안 됩니다.
- (다) 아니요, 로그가 비어서 나온 「거부율 0%」는 안전하다는 뜻이 아닙니다.
  - 요청이 하나도 없으면 거부율은 계산할 수 없는데, 0.0 을 리턴하도록 막아 두었기 때문에 0% 로 나온 것입니다.
  - 그래서 보고서 1절의 「전체 요청: 0건」을 함께 봐야 합니다. 요청이 0건이면 서버가 멈췄거나 로그를 못 모은 것일 수 있어서 서버와 로그 수집부터 확인합니다.
  - 0 으로 나누는 것을 막지 않으면 `ZeroDivisionError` 가 나서 보고서 자체가 만들어지지 않고, 담당자는 「요청이 없었다」가 아니라 「프로그램이 고장 났다」로 받아들입니다. 아래 「자주 틀리는 곳」에서 실제로 확인합니다.

<h2>왜</h2>

- 로그는 한 줄씩 쌓이기만 하므로 읽고 세어 비율로 바꿔야 의미가 생깁니다.
  - 경고 기준은 `config/alert.json` 에 두어서 기준만 바꿀 때 코드를 고치지 않습니다.

<h2>자주 틀리는 곳</h2>

- `count_by` 에서 `old_count` 를 쓰지 않고 `counts[value] = 1` 로 쓰면 오류는 나지 않지만 모든 횟수가 1 이 됩니다.
  - 실행하면 다음처럼 됩니다(거부 사유가 모두 1 이고 「거부 4 번 이상 사용자」가 비면 이 실수입니다).

```
--- 단계 1: 집계 - 요청 40 건
허용 24 · 거부 16 · 거부율 40%
--- 단계 2: 거부 사유별
역할이 없음 1
업무 시간 밖 1
퇴사한 계정 1
허용되지 않은 접속 위치 1
--- 단계 3: 경고 기준
거부율 40% >= 기준 30% -> 경고
거부 4 번 이상 사용자: []
```

- `deny_rate` 의 8 · 9번을 빼먹으면 이번 로그에서는 잘 되지만, 빈 로그로 실행하면 다음 오류가 납니다.
  - 직접 시험하려면 `access_control` 폴더에 빈 파일 `empty.jsonl` 을 만들고, `apply5-1_run.py` 의 `LOG_PATH = "week_log.jsonl"` 을 `"empty.jsonl"` 로 바꿔 실행합니다. 시험이 끝나면 `"week_log.jsonl"` 로 되돌립니다.

```
Traceback (most recent call last):
  File "…/access_control/apply5-1_run.py", line 10, in <module>
    rate = deny_rate(entries)                                        # 거부율(0 ~ 1)을 구한다
  File "…/access_control/log_summary.py", line 49, in deny_rate
    return denied / total                                        # 거부 수를 전체 수로 나눈 비율을 리턴한다
           ~~~~~~~^~~~~~~
ZeroDivisionError: division by zero
```

  - `log_summary.py` 의 줄 번호(`line 49`)는 직접 쓴 줄 수에 따라 사람마다 다릅니다. `ZeroDivisionError: division by zero` 가 같으면 이 실수입니다.

  - 8 · 9번을 쓰고 같은 빈 로그로 실행하면 다음처럼 오류 없이 끝납니다.

```
--- 단계 1: 집계 - 요청 0 건

--- 단계 2: 거부 사유별
--- 단계 3: 경고 기준
```

<h2>관제에서는</h2>

- 로그 집계는 관제의 기본이고, 거부율이 갑자기 오르면 먼저 거부 사유와 사용자를 봅니다.
  - 경고는 공격이라는 뜻이 아니라 「먼저 살펴볼 곳」입니다.
  - 요청이 0개인 주는 로그 수집이 끊겼을 수 있으므로 따로 알립니다.
