# Exercise 1-1 · 사용자 파일과 역할 파일 만들기

## 읽기 · 왜 사용자·역할 표가 필요한가

> **읽을거리 — 읽기만 합니다.** 문제가 아닙니다. 답할 질문도, 따라 칠 명령도 없습니다.

1. 앞선 사건에서 seoyeon 계정은 맡은 자원(영업 실적)이 아닌 정산 내역을 조회했는데, 막는 규칙이 없어서 통과했습니다. 「누가 무엇을 해도 되나」가 어디에도 적혀 있지 않았기 때문입니다.
2. 직원마다 권한을 하나씩 주면 직원이 수백 명일 때 관리가 안 됩니다. 부서를 옮긴 직원의 권한이 그대로 남아 필요 이상의 권한이 쌓입니다.
3. Unit 1에서 만드는 사용자 · 역할 파일과 판정 함수는 Unit 2의 정책(`policy.py`), Unit 4의 요청 · 승인 흐름에서 그대로 불러 씁니다.

## 읽기 · 1.1 인증과 인가

> **읽을거리 — 읽기만 합니다.** 문제가 아닙니다. 답할 질문도, 따라 칠 명령도 없습니다.

- **인증**(authentication · 오센티케이션)
  - 「이 사람이 누구인가」를 확인하는 것
  - 예: 비밀번호 · MFA 로 로그인
- **인가**(authorization · 오서라이제이션)
  - 「이 사람이 이 자원에 이 일을 해도 되나」를 정하는 것
  - 예: 영업팀은 영업 실적을 조회할 수 있지만 정산 내역은 조회할 수 없다
- 인증을 통과해도 인가에서 막힐 수 있습니다. 이 사건은 비밀번호로 인증은 됐고, **인가를 확인하는 곳이 없었습니다.**
- 아래 그림의 **`SETTLE` 은 약자가 아니라 영어 단어 settle(정산하다, 결제를 마무리하다)입니다.** `SETTLE:QUERY` 는 「정산 쪽 조회 업무」라는 분류 이름으로 읽습니다.

```
+---------------------------------------------------------+
| 요청: seoyeon 이 정산 내역(SETTLE)을 조회(QUERY)하려 함 |
+---------------------------------------------------------+
   |
   v
+-----------------+
| 인증: 누구인가? |
+-----------------+
   |
   +--> seoyeon 맞음 (비밀번호 통과)
   |
   v
+--------------------------+
| 인가: 이 일을 해도 되나? |
+--------------------------+
   |
   +--> 영업 역할에는 SETTLE 조회 권한이 없음 --> 거부
```

## 읽기 · 1.2 역할 기반 접근통제(RBAC)

> **읽을거리 — 읽기만 합니다.** 문제가 아닙니다. 답할 질문도, 따라 칠 명령도 없습니다.

- **RBAC**(Role-Based Access Control · 롤 베이스드 액세스 컨트롤, 역할 기반 접근통제)
  - 사용자에게 권한을 직접 주지 않고, **역할**에 권한을 주고 사용자에게 역할을 준다
  - 사용자 → 역할 → 권한 순서로 따라가서 허용 여부를 정한다
- **역할**(role · 롤)
  - 하는 일이 같은 사람들의 묶음
  - 예: 영업(sales) · 재무(finance) · 계정 관리자(account_admin)
- **권한**(permission · 퍼미션)
  - 「자원 하나에 행위 하나」를 허용하는 것
  - 오늘은 `자원:행위` 모양으로 쓴다. 예: `SALES:QUERY` 는 영업 실적 조회

```
  사용자          역할                  권한
+---------+     +---------------+     +-------------------------------+
| seoyeon | --> | sales         | --> | SALES:QUERY, SALES:CHANGE     |
+---------+     +---------------+     +-------------------------------+
| junho   | --> | finance       | --> | SALES:QUERY, SETTLE:QUERY     |
+---------+     +---------------+     +-------------------------------+
| gaeun   | --> | account_admin | --> | ACCOUNT:QUERY, ACCOUNT:CHANGE |
+---------+     +---------------+     +-------------------------------+
```

권한을 「준다」는 것은 그 사람이 할 수 있는 일을 파일에 적어 두는 것입니다. 영업팀이 30명이라고 할 때 두 방식을 파일 모양으로 비교하면 이렇습니다.

```
[직접 주기] 사용자 한 명마다 권한 리스트를 적는다 (30명이면 30곳)

   "seoyeon": {"permissions": ["SALES:QUERY", "SALES:CHANGE"]},
   "minsu":   {"permissions": ["SALES:QUERY", "SALES:CHANGE"]},
   ...                          ← 영업팀 30명 모두 같은 내용을 되풀이해 적는다

   영업팀 권한이 바뀌면      30곳을 하나씩 고친다
   부서를 옮긴 직원은        옛 권한을 지우는 것을 잊기 쉽다

[역할로 주기] 권한 리스트는 역할 한 곳에만 적고, 사용자에게는 역할 이름만 적는다

   roles.json  "sales": ["SALES:QUERY", "SALES:CHANGE"]        ← 권한은 여기에 한 번만 적는다
   users.json  "seoyeon": {"role": "sales"},                   ← 30명은 역할 이름만 적는다
               "minsu":   {"role": "sales"},
               ...

   영업팀 권한이 바뀌면      roles.json 의 sales 한 곳만 고친다
   부서를 옮긴 직원은        그 직원의 role 한 칸만 바꾼다
```

- 영업팀 30명 중 1명이 재무팀으로 옮길 때 고칠 곳을 세면, 직접 주기는 영업 권한 두 개(`SALES:QUERY` · `SALES:CHANGE`)를 빼고 재무 권한 두 개(`SALES:QUERY` · `SETTLE:QUERY`)를 넣어야 하므로 **네 군데**를 고칩니다. 하나라도 빼먹으면 옛 권한이 남습니다. 역할로 주기는 그 직원의 역할 하나(`sales` → `finance`)만 바꾸는 **한 군데**입니다.

## 읽기 · 1.3 권한 매트릭스와 최소권한

> **읽을거리 — 읽기만 합니다.** 문제가 아닙니다. 답할 질문도, 따라 칠 명령도 없습니다.

- **권한 매트릭스**(permission matrix · 퍼미션 매트릭스)
  - 역할을 줄에, 권한을 칸에 놓고 허용(○)과 아님을 표시한 표
  - 누가 무엇을 해도 되는지를 한눈에 확인하는 데 쓴다
- **최소권한**(least privilege · 리스트 프리빌리지)
  - 일에 필요한 만큼만 허용한다
  - 매트릭스에서는 ○ 가 적을수록 좋다. 필요 없는 ○ 는 사고가 났을 때 피해 범위가 된다
- **기본 거부**(default deny · 디폴트 디나이)
  - 매트릭스에 ○ 가 없으면 모두 거부한다(앞선 실습의 방화벽과 같은 생각)

표에 나오는 자원과 행위입니다.

- 자원
  - `SALES`: 영업 실적
  - `SETTLE`: 정산 내역
  - `ACCOUNT`: 직원 계정과 그 권한 설정
- 행위
  - `QUERY`: 조회
  - `CHANGE`: 변경
- 역할 `batch` 는 **서비스 계정**(사람이 아니라 프로그램이 자동으로 쓰는 계정)의 역할입니다. `batch-night` 가 매일 02:00 에 정산을 집계합니다.

A사가 정한 권한 매트릭스(초안)입니다.

| 역할 | `SALES:QUERY` | `SALES:CHANGE` | `SETTLE:QUERY` | `ACCOUNT:QUERY` | `ACCOUNT:CHANGE` |
|---|---|---|---|---|---|
| `sales`(영업) | ○ | ○ | | | |
| `finance`(재무) | ○ | | ○ | | |
| `account_admin`(계정 관리자) | | | | ○ | ○ |
| `batch`(정산 집계 서비스 계정) | | | ○ | | |
| `auditor`(감사) | ○ | | ○ | ○ | |

- `auditor`(감사 담당)의 **감사**(audit · 오딧)는 규칙대로 일이 처리됐는지 나중에 기록으로 확인하는 일입니다. 이 역할은 자료를 조회만 하고 바꾸지는 않습니다.
- 역할이 하는 일은 다음과 같습니다.
  - `sales`: 영업 실적을 조회하고 고칩니다.
  - `finance`: 정산 내역을 조회합니다.
  - `account_admin`: 직원 계정과 권한을 설정합니다.
  - `batch`: 정산을 자동으로 집계합니다.
  - `auditor`: 자료를 조회하며 확인합니다.

#### 매트릭스에서 요청 하나 판정하기

읽는 법은 역할 줄과 권한 칸이 만나는 곳을 보는 것입니다.

- 예 ①: `sales` 줄 × `SALES:QUERY` 칸 = ○ → 영업은 영업 실적을 조회해도 됩니다.
- 예 ②: `sales` 줄 × `SETTLE:QUERY` 칸 = 빈칸 → 영업이 정산 내역을 조회하면 거부입니다.

요청 하나는 세 단계로 판정합니다. 본보기는 문제에 없는 요청입니다.

| 단계 | 하는 일 | 본보기: gaeun 의 직원 계정 조회(`ACCOUNT:QUERY`) |
|---|---|---|
| ① 역할 찾기 | 사용자의 역할을 인사팀 표에서 찾는다 | gaeun 의 역할은 `account_admin` |
| ② 칸 찾기 | 그 역할 줄과 요청한 권한 칸이 만나는 곳을 본다 | `account_admin` 줄 × `ACCOUNT:QUERY` 칸 |
| ③ ○ 확인 | ○ 가 있으면 허용, 없으면 거부 | ○ 있음 → 허용 |

- 다른 본보기: `auditor` 가 `ACCOUNT:CHANGE` 를 하려는 경우 그 칸에 ○ 가 없으므로 거부입니다(앞선 실습에서 본 방화벽의 기본 거부와 같습니다).

## 읽기 · 1.4 JSON 으로 사용자 파일 만들기

> **읽을거리** — 다음 문제의 배경지식입니다. 읽고 나서 아래 「Exercise」로 갑니다.

매트릭스를 코드가 읽으려면 파일로 적어야 합니다. 앞선 실습에서 배운 **JSON** 으로 씁니다. 오늘은 파일 두 개를 `config` 폴더에 둡니다.

| 파일 | 담는 것 | 모양 |
|---|---|---|
| `config/users.json` | 사용자 → 역할 · 재직 여부 | `"사용자": {"role": "역할", "employed": true}` |
| `config/roles.json` | 역할 → 권한 리스트 | `"역할": ["자원:행위", …]` |

- 설정을 코드와 나눠 파일에 두면, 직원이 바뀌어도 코드는 그대로 두고 파일만 고칩니다.
- JSON 의 참 · 거짓은 소문자 `true` · `false` 로 씁니다. 파이썬의 `True` · `False` 와 다릅니다.
- 마지막 항목 뒤에는 쉼표를 쓰지 않습니다.
- 문자열과 이름은 큰따옴표 `"` 로만 감쌉니다. 작은따옴표 `'` 는 JSON 오류입니다.
- 파일이 JSON 규칙에 맞는지는 `python -m json.tool config/users.json` 처럼 확인합니다. `-m json.tool` 은 파이썬에 들어 있는 JSON 검사 도구를 실행하라는 뜻입니다. 맞으면 내용이 다시 정리되어 출력되고, 틀리면 `Expecting …` 오류와 줄 번호가 나옵니다.

#### 매트릭스의 ○ 는 파일에서 어떻게 적히나

- 매트릭스의 ○ 는 사람이 보기 쉽게 그린 표시입니다. 파일에는 「○」 글자로 저장하지 않고, `roles.json` 리스트에 적힌 **권한 하나가 ○ 한 칸**입니다. 빈칸은 아예 적지 않으므로 리스트에 없으면 거부(기본 거부)입니다.
  - 예: `sales` 줄의 ○ 두 칸(`SALES:QUERY` · `SALES:CHANGE`) → `"sales": ["SALES:QUERY", "SALES:CHANGE"]`

두 파일은 역할 이름으로 이어집니다. seoyeon 이 무엇을 해도 되는지는 두 파일을 차례로 보면 압니다.

| 순서 | 파일 | 찾는 것 | 결과 |
|---|---|---|---|
| ① | `users.json` | `"seoyeon"` 줄 | `"role": "sales"` |
| ② | `roles.json` | `"sales"` 줄 | `["SALES:QUERY", "SALES:CHANGE"]` |
| ③ | 결과 | | seoyeon 은 영업 실적 조회 · 변경만 해도 됨 |

- 두 파일을 잇는 열쇠는 **역할 이름**입니다. `users.json` 의 `role` 과 `roles.json` 의 이름이 같은 문자열이어야 하고, `"Sales"` · `"sale"` 처럼 다르면 `roles.json` 에서 못 찾습니다.
- 권한은 `roles.json` 에 역할마다 한 번만 적고, 영업팀 30명은 `users.json` 에 역할 이름만 적습니다.
- 쉼표 하나 · 따옴표 하나만 틀려도 판정 코드가 파일을 읽지 못합니다. 그때 `python -m json.tool` 이 틀린 줄 번호와 함께 오류를 알려 줍니다(아래는 Python 3.9 에서 확인한 문구이고, 버전에 따라 조금 다를 수 있습니다. 줄 번호는 내 파일에 따라 다릅니다).

| 틀린 곳 | `json.tool` 이 보여 주는 오류(예) |
|---|---|
| 줄 끝 쉼표가 빠짐 | `Expecting ',' delimiter: line 3 …` |
| 작은따옴표 `'seoyeon'` | `Expecting property name enclosed in double quotes: line 2 …` |
| 마지막 줄 뒤에 쉼표 | `Expecting property name enclosed in double quotes: line 4 …` |
| 파이썬식 `True` | `Expecting value: line 2 …` |

> **여기부터 문제입니다.** 위는 읽을거리였고, 아래에서 직접 합니다.

## Exercise 1-1 · 사용자·역할 파일 만들고 약점 따지기

**이런 상황이 있습니다**

- 보안 담당이 「매트릭스 초안대로라면 요청들이 어떻게 판정되는지, 필요 이상의 ○ 가 있는지 먼저 봐 달라」고 합니다.
- 그다음에는 인사팀이 보낸 계정 리스트와 매트릭스를 판정 코드가 읽을 수 있는 파일 두 개로 옮겨야 합니다.
- 현업에서는 접근통제를 코드로 옮기기 전에 표를 놓고 요청 몇 건으로 판정이 맞는지 먼저 확인합니다. 인사 시스템의 리스트를 접근통제 시스템으로 옮기는 일은 매일 일어나고, 퇴사자 표시가 빠지면 퇴사한 사람의 계정이 살아 있게 됩니다. Exercise 1-2에서 쓸 판정 함수는 `employed` 가 `false` 이면 그 사용자를 거부합니다.

**할 일**

1. 요청 여섯 건을 1.3 의 매트릭스로 <mark>판정</mark>하고, <mark>필요 이상으로 보이는 ○</mark> 를 찾습니다.
2. 인사팀 계정 리스트로 <mark>`config/users.json`</mark> 을 **직접** 씁니다.
3. 매트릭스로 <mark>`config/roles.json`</mark> 의 세 역할을 **직접** 씁니다.
4. 두 파일을 <mark>`python -m json.tool`</mark> 로 확인하고, 파일의 <mark>약한 점</mark>(퇴사 반영이 늦을 때, 더 필요한 칸, 역할이 없는 사용자)을 따져 봅니다.

**받은 자료 ①** — 요청 여섯 건

| 요청 | 사용자(역할) | 하려는 일 |
|---|---|---|
| ① | seoyeon(`sales`) | `SALES:QUERY` |
| ② | seoyeon(`sales`) | `SETTLE:QUERY` |
| ③ | junho(`finance`) | `SETTLE:QUERY` |
| ④ | junho(`finance`) | `SALES:CHANGE` |
| ⑤ | gaeun(`account_admin`) | `SETTLE:QUERY` |

**받은 자료 ②** — 인사팀 계정 리스트

| 사용자 | 역할 | 재직 |
|---|---|---|
| `seoyeon` | `sales` | 재직 중 |

**순서**

1. 요청마다 사용자의 역할 줄을 찾고, 하려는 일의 칸에 ○ 가 있는지 봅니다. ○ 가 없으면 기본 거부입니다.
   - 다음으로 역할마다 ○ 를 하나씩 보며 「이 역할이 하는 일에 꼭 필요한가」를 따집니다. 계정 설명(영업은 영업 실적, 재무는 정산)을 떠올립니다.
   - 여기서 **보고서 (가) · (나)** 를 먼저 씁니다.
2. **[터미널]** 위치가 `…/access_control` 인지 확인합니다.
   ```bash
   pwd
   ```
   - 명령 풀이: `pwd` 지금 있는 폴더의 위치를 보여 줌
3. **[VS Code 또는 터미널]** `access_control` 폴더 안에 `config/users.json` 파일을 만듭니다. 아래 세 가지 방법 중 **하나만** 고릅니다.
   - **방법 1 · VS Code 에서 만들기**
     1. VS Code 왼쪽 목록에서 `access_control` 폴더를 클릭해 선택합니다(선택하지 않으면 다른 폴더에 만들어집니다).
     2. 목록 위쪽의 **새 파일**(New File, 파일 모양에 `+`) 아이콘을 누릅니다.
     3. 이름 칸에 `config/users.json` 이라고 입력하고 Enter 를 누릅니다. 앞쪽 폴더가 아직 없으면 함께 만들어집니다.
     4. 열린 파일에 내용을 입력하고 저장합니다.
   - **방법 2 · touch**: `touch config/users.json` → VS Code 에서 파일을 열어 내용을 입력
   - **방법 3 · vim 으로 만들기**: `vim config/users.json` → `i` → 글 입력 → `Esc` → `:wq` Enter
4. **[vim 또는 VS Code]** 위 **받은 자료 ②** 의 표를 보고 `config/users.json` 을 씁니다. 표의 한 줄(사용자 한 명)이 파일의 한 줄이 됩니다. 첫 사용자 `seoyeon` 은 이렇게 옮깁니다.

   | 표의 칸 | 표에 적힌 값 | 파일에 쓰는 모양 |
   |---|---|---|
   | 사용자 | `seoyeon` | 큰따옴표 안의 이름 `"seoyeon":` |
   | 역할 | `sales` | `"role": "sales"` |
   | 재직 | 재직 중 | `"employed": true` (퇴사면 `false`) |

   이 세 칸을 한 줄로 합치면 아래와 같습니다. `{` 는 파일 맨 위에 한 번 쓰는 시작 표시입니다.
   ```json
   {
     "seoyeon": {"role": "sales", "employed": true},
   ```
   표의 두 번째 줄 `junho` 부터 여섯 번째 줄 `tester` 까지 **다섯 명**을 같은 방법으로 한 줄씩 **직접** 이어서 씁니다. 사용자 이름과 역할은 표의 글자를 그대로 옮기고, 재직 칸만 보고 `true` 와 `false` 를 고릅니다.
   - 줄 끝마다 쉼표를 쓰고, **마지막 사용자 줄 뒤에는 쉼표 없이** 다음 줄에 `}` 를 씁니다(파일 맨 아래 닫는 표시).
   - 표에서 `퇴사` 인 사람만 `"employed": false` 이고, `재직 중` 이면(서비스 계정 `batch-night` 도 포함) `true` 입니다.
5. **[터미널]** JSON 규칙에 맞는지 확인합니다. 여섯 명이 다시 출력되면 됩니다.
   ```bash
   python -m json.tool config/users.json
   ```
   - 명령 풀이: `python -m json.tool` 파이썬의 JSON 검사 도구를 실행 · `config/users.json` 검사할 파일
   - `Expecting ',' delimiter: line 4` 처럼 나오면 그 줄 근처의 쉼표 · 따옴표를 봅니다.
6. **[VS Code 또는 터미널]** `access_control` 폴더 안에 `config/roles.json` 파일을 만듭니다. 아래 세 가지 방법 중 **하나만** 고릅니다.
   - **방법 1 · VS Code 에서 만들기**
     1. VS Code 왼쪽 목록에서 `access_control` 폴더를 클릭해 선택합니다(선택하지 않으면 다른 폴더에 만들어집니다).
     2. 목록 위쪽의 **새 파일**(New File, 파일 모양에 `+`) 아이콘을 누릅니다.
     3. 이름 칸에 `config/roles.json` 이라고 입력하고 Enter 를 누릅니다. 앞쪽 폴더가 아직 없으면 함께 만들어집니다.
     4. 열린 파일에 아래 내용을 복사해 붙여 넣고 저장합니다.
   - **방법 2 · touch**: `touch config/roles.json` → VS Code 에서 파일을 열어 아래 내용을 복사해 붙여 넣고 저장합니다
   - **방법 3 · vim 으로 만들기**: `vim config/roles.json` → `i` → 아래 내용을 붙여넣기 → `Esc` → `:wq` Enter
   ```json
   {
     "sales": ["SALES:QUERY", "SALES:CHANGE"],
     "account_admin": ["ACCOUNT:QUERY", "ACCOUNT:CHANGE"]
   }
   ```
   - 위 두 역할은 미리 적어 두었습니다. `"account_admin"` 줄 아래에 1.3 의 매트릭스를 보고 `finance` · `batch` · `auditor` 세 역할을 **직접** 씁니다. 권한은 매트릭스의 ○ 칸을 왼쪽부터 순서대로 씁니다.
   - `"account_admin"` 줄 끝에 쉼표를 추가하고, 새로 쓴 마지막 줄 뒤에는 쉼표를 쓰지 않습니다. 마지막 줄 뒤에 쉼표를 쓰면 JSON 오류가 나서 판정 코드가 파일을 아예 읽지 못합니다.
7. **[터미널]** 확인합니다. 역할 다섯 개가 출력되면 됩니다.
   ```bash
   python -m json.tool config/roles.json
   ```
   - 명령 풀이: `python -m json.tool` 파이썬의 JSON 검사 도구를 실행 · `config/roles.json` 검사할 파일
   - 여기서 **보고서 (다)** 를 먼저 씁니다.
