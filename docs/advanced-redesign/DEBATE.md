# Unit 토론 규칙

Unit마다 세 역할이 토론해 원고를 고친다. 기준은 `BRIEF.md`(시나리오·생각법·주소 장부·기술 정확성 주의)와 `../QUIZ_AUTHORING_RULES.md`.

## 역할

| 역할 | 관점 | 기록 파일 |
| --- | --- | --- |
| 독자 | 기본편 Unit 1~10만 마친 비전공 AX 실무자. 처음 읽는 사람처럼 Page 순서대로 읽는다 | `debate/u{N}-reader.md` |
| 검수자 | 네트워크·보안 실무 엔지니어 겸 교육 설계자 | `debate/u{N}-tech.md` |
| 편집자 | 두 지적을 저울질해 원고를 실제로 고친다 | `debate/u{N}-editor.md` |

## 독자가 보는 것

- 이 Page를 왜 읽는지 첫 문단에서 알겠는가. 지루하거나 같은 말을 되풀이하는 곳.
- **너무 길거나 많은 곳**: 줄여도 이해가 안 깨지는 문단·표·예시. 한 Page에 개념이 너무 많은 곳.
- 설명 없이 나오는 용어, 앞에서 안 배운 전제, 따라가다 막히는 문장.
- 퀴즈가 본문만 읽고 풀리는가, 너무 쉽거나(정답이 티 남) 애매한가.

## 검수자가 보는 것

- 기술 오류·과장·오해를 부르는 단순화. 근거 없는 수치.
- Lesson 사이 모순(주소·장면·사실), 다른 Unit과 중복되거나 안 맞는 연결.
- 퀴즈 정답이 틀렸거나 둘 이상 맞을 수 있는 문항, 오답 품질.
- 제목이 기준(독자의 문제·질문)에 맞는가, 생각법이 장식에 그치지 않는가.

## 지적 형식 (독자·검수자 공통)

항목마다 번호, `심각도(상/중/하)`, `파일·Page 제목(또는 문항 ID)`, `문제`, `제안(바꿀 문장이나 삭제 범위)`. 상 항목부터. 칭찬은 3줄 이내. 최대 25항목.

## 편집자 절차

1. 두 기록을 모두 읽고, 항목마다 **수용 / 부분 수용 / 기각**과 한 줄 이유를 `u{N}-editor.md`에 표로 남긴다. 두 사람이 엇갈리면 근거를 비교해 정한다.
2. 수용한 것을 원고에 반영한다.
3. 반박 라운드: 독자·검수자가 기각 항목 중 다시 주장할 것만 짧게 반박하면, 편집자가 최종 결정하고 같은 파일에 덧붙인다.

## 편집 제약

- Lesson ID·Page ID·문항 ID를 바꾸지 않는다. Page 수는 6~8 범위 안에서만 바꾸며, 바꾸면 이유를 적는다.
- `question_placements.after_paragraph`는 1 이상, 문단 수 미만이어야 하고 개념 문단 바로 뒤를 가리켜야 한다(빈 줄로 나뉜 블록, 표 하나 = 한 블록). 문단을 고친 뒤 다시 맞춘다.
- 정답 위치는 a~e에 고르게, Lesson 안에서 같은 글자가 연달아 나오지 않게.
- `docs/advanced-restructure-*`, `docs/advanced-route-aliases.json`, `scripts/`, `course.yaml`은 건드리지 않는다.
- 끝나면 `python3 scripts/build_course.py --output /tmp/u{N}.json`과 `python3 scripts/audit_svg_steps.py`가 통과해야 한다.

## 보기 길이 기준 (2026-11-14 추가)

정답이 가장 긴 보기인 문항이 Unit 11·13·14에서 70~95%였다. 가장 긴 보기만 고르면 본문을 안 읽어도 풀린다.

- 정답이 **혼자 가장 긴 보기**인 비율을 Unit마다 **35% 이하**로 맞춘다: `python3 scripts/audit_quiz_choice_length.py <unit 폴더>`.
- 방법: 정답을 줄이고(이유는 피드백으로 옮긴다), 오답 중 1~2개를 정답만큼 구체적으로 쓴다. 오답도 그럴듯한 조건·이유를 갖춰야 한다.
