1. Page 「상대가 바뀌면 바깥 포트도 바뀔까?」
   - 이전: 같은 내부 통신이 어느 상대와 통신하든 같은 바깥 주소·포트를 쓰는 것을 상대와 무관한 매핑(EIM)이라 하고, 상대마다 다른 바깥 포트를 배정하는 것을 상대에 따라 달라지는 매핑이라 한다(상대의 IP만 볼지, IP·포트를 모두 볼지는 장비마다 다르다).
   - 이후: …쓰면 상대와 무관한 매핑(EIM)이라 한다. 상대마다 다른 바깥 포트를 배정하면 …매핑이라 한다. 다만 상대의 IP만 볼지, IP·포트를 모두 볼지는 장비마다 다르다.
   - 이유: 142자 한 문장에 정의 둘과 괄호 단서가 들어 있어 정의마다 한 문장으로 나누고 단서를 "다만"으로 분리했다.
2. Page 「NAT에게 꼭 따로 물어야 할 두 가지는?」
   - 이전: 첫째 질문은 …새로 붙이는지 같은 번호를 쓰는지이고, 둘째 질문은 …누구 것이든 받는지다. 두 질문은 따로 답할 수 있으므로, …알 수 없다.
   - 이후: 안내 데스크로 바꿔 말하면 이렇다. 첫째 질문은 …쓰는지다. 둘째 질문은 …받는지다. 두 질문은 따로 답할 수 있다. 그래서 …알 수 없다.
   - 이유: 121자에 질문 둘이 한 문장이어서 질문마다 한 문장으로 나눴다(비유는 그대로).

4. Page 「상대가 바뀌면 바깥 포트도 바뀔까?」 첫 문단
   - 이전: 주소 확인 서버(`203.0.113.60`)는 이 PC를 …`192.0.2.123:40001`로 봤고, 앱이 그 주소를 협력사 담당자에게 알려 줬다.
   - 이후: 주소 확인 서버(`203.0.113.60`)는 바깥에서 본 주소를 알려 주는 서버다. 이 서버는 PC를 …로 봤다. 앱은 그 주소를 협력사 담당자에게 알려 줬다.
   - 이유: 처음 나온 "주소 확인 서버"에 한 구절 풀이를 달고 두 사건을 나눴다.
5. Page 「Full Cone, Symmetric은 어떻게 읽을까?」
   - 이전: …옛 분류다(STUN 초판인 RFC 3489의 용어이고, 현재 표준 RFC 4787은 둘을 따로 설명한다).
   - 이후: …옛 분류다. 바깥 주소를 알려 주는 프로토콜 STUN의 초판(RFC 3489)에서 쓰던 용어다. 현재 표준 RFC 4787은 둘을 따로 설명한다.
   - 이유: 괄호 안에 든 두 사실을 문장 둘로 풀고 STUN이 무엇인지 덧붙였다(STUN 설명은 Page 6에서 이어진다).
6. Page 「누가 보낸 패킷까지 받아 줄까?」
   - 이전: 같은 IP만 받는 방식은 IP만 보므로 받아 주고, 같은 IP·포트만 받는 방식은 포트까지 보므로 받지 않는다.
   - 이후: 같은 IP만 받는 방식은 IP만 보므로 받아 준다. 같은 IP·포트만 받는 방식은 포트까지 보므로 받지 않는다.
   - 이유: 핵심 비교 두 가지를 문장 하나씩으로 나눠 결과가 갈리는 것을 눈에 띄게 했다.

   - 이후: 박 팀장 쪽이 먼저 패킷을 보내는 경우를 보자. 지우 쪽 공유기가 …방식이면 그 패킷을 막을 수 있다. 지우 쪽에서 먼저 나간 기록이 없기 때문이다.
   - 이유: 조건과 결과를 나누고 모호한 "우리 쪽"을 "지우 쪽"으로 바로잡았다.
