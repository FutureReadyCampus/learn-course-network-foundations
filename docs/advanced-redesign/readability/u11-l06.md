## 대표 수정

**패킷은 잡았는데 왜 못 읽을까?**
1. 이전: 회사 프록시 기록에는 플러그인이 외부 AI API로 언제, 얼마나 보냈는지만 남아 있다. → 이후: ...보낸 시각과 양만 남아 있다. / 이유: 의문절 "언제, 얼마나 보냈는지"를 명사로 줄여 부담을 낮춤.
2. 이전: ...그 뒤의 Payload는 알아볼 수 없는 바이트로 가득하다. → 이후: ...헤더는 읽힌다. 그런데 헤더 뒤에 실린 내용인 Payload는... / 이유: 문장 분리, 처음 나온 Payload 풀이.
3. 이전: ...그대로 두고, 그 안에 실린 HTTP 요청...만 암호문으로 바꾼다. ...세션 키가 없는 → 이후: 두 문장으로 나누고 "세션 키(암호를 푸는 열쇠)" / 이유: 90자 문장 분리, 용어 풀이.
4. 이전: ...맨 앞에는 "...이어 달라"는 짧은 부탁(CONNECT 요청)이 평문으로 찍혀 있다. → 이후: ...회사 프록시다. 맨 앞에는 ... / 이유: 108자 문장 분리.

**내 PC 안에 중계소를 세운다면?**
5. 이전: 앱이 이 도구를 프록시로 쓰도록 설정하면, 앱의 요청은 도구에 먼저 도착하고, 도구가 새 연결로 ... 돌려준다. → 이후: 요청 도착 / 도구가 전달 / 응답 반환을 세 문장 흐름으로 분리. / 이유: "~하고 ~하고" 나열 해소, 주어 명확화.
6. 이전: 회사 프록시는 ...운영하지만, 로컬 프록시는 ...켠다. → 이후: 두 문장으로 나눠 회사/로컬 대비. / 이유: 89자 대조 문장 분리.

**127.0.0.1:8080은 어디로 가는 주소일까?**
7. 이전: ...소켓으로 실제 목적지에 연결한다. → 이후: 소켓(프로그램이 연결을 주고받는 출입구) / 이유: 처음 나온 용어 풀이.
8. 이전: 직접 외부 연결이 막혀 있으니, 도구가 바깥으로 나갈 때 ...상위 프록시 칸에 적어 둔다. → 이후: "도구도 바깥으로 나갈 때 회사 프록시를 거쳐야 한다. 그래서 ...칸에 회사 프록시를 적어 둔다." / 이유: 87자, 무엇을 적는지 주어·목적어 명시.
9. 이전: 어떤 앱은 ~를 따르고, 어떤 앱은 ~해야 하며, 어떤 앱은 ~무시한다. → 이후: 세 문장 / 이유: 병렬 나열 분리.

**로컬 프록시는 HTTPS를 어떻게 열어 볼까?**
10. 이전: 앱이 운영체제의 신뢰 목록 대신 ...쓰거나, ...인증서 고정을 쓰면 ...거부해 연결 자체가 실패할 수 있다. → 이후: 세 문장으로 분리. / 이유: 115자 최장 문장.
11. 이전: 도구는 ...갖고 있지 않으니, 그 자리에서 ...만들어 내민다. 브라우저 입장에서는 → 이후: "...갖고 있지 않다. 그래서 ...만들어 내민다. 브라우저가 보기에는" / 이유: 원인-결과를 문장으로 분리, 번역투 "입장에서는" 제거.

**패킷 조각 대신 요청 한 건으로 보려면?**
12. 이전: 앱이 한 번에 넘긴 데이터를 여러 세그먼트로 나눠 보내고, 받는 쪽 TCP가 ...이어 붙인다. → 이후: "TCP는 ...세그먼트(조각)로 나눠 보낸다. 받는 쪽 TCP는 ..." / 이유: 주어 TCP 명시, 세그먼트 풀이.
13. 이전: ...base64로 바꾸면 크기가 약 4/3배로 커지기 때문이다. → 이후: base64(파일을 글자로 바꾸는 방식) / 이유: 처음 나온 용어 풀이.
