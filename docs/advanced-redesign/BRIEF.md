# 심화편(Unit 11~15) 재설계 기준서

2026-11-14 사용자 확정. 모든 설계·집필 agent는 이 문서를 기준으로 삼는다.

## 왜 다시 쓰나 (사용자 지적)

1. Lesson·Page 제목이 구미를 당기지 않는다. 개념 이름만 나열돼 있다.
2. Page를 열어도 이걸 왜 배우는지 모르겠다.
3. AX(AI 전환)를 하며 필요한 컴퓨터적 사고에 대한 언급이 없다.
4. Lesson당 Page 수가 4~20으로 들쭉날쭉하다.

## 2차 확정 (2026-11-14, 설계안 5개와 Luna 검토 뒤)

| 항목 | 결정 |
| --- | --- |
| Module 3~5 연결 | 지우는 **신입 IT·보안 담당**. 박 팀장·서 이사는 문제 제기와 정책 결정 역할 유지. 각 Unit 마지막 Page 끝에 **다리 문단** 하나: 그 Unit에서 실제로 남은 반복 작업을 짚고 다음 Module(3 접근통제 자동화 / 4 이상탐지 자동화 / 5 자동대응)을 한두 문장 예고. 자동화 자체는 가르치지 않는다. Unit 15는 세 Module을 한 번에 예고 |
| 원고 밖 보강 | **장면에 꼭 필요한 것만**. 넣을 것: SNI, 헤어핀 NAT, NAT-T, 전체/분할 터널, 이상 행위 기반 탐지, 802.1X(이름만). MTU·사전 공유 키/인증서·DHCP 예약 등은 한두 문장. 넣은 것은 RFC·표준을 출처 메모에 적는다 |
| 그림 | **본문·퀴즈 먼저**. 기존 그림은 내용이 맞는 Page에만 다시 붙이고, 주소·이야기가 어긋나는 그림(옛 동아리 문구, 실제 공인 IP)은 뺀다. 새 그림은 Lesson별 후속 작업 |
| 집필 순서 | Unit 11 먼저 PR → 사용자 확인 → Unit 12~15 동시 |
| 제목 | 설계안 제목 그대로 (사용자 이의 없음) |

기본값(사용자에게 보고함, 이의 시 변경):

- 도쿄 쇼룸 = Unit 13의 해외 거점 = Unit 14의 VPN 지사.
- Unit 12의 포트 포워딩은 **고객 시연 기간에만 열었다 닫는다**. 상시 원격 접속은 Unit 14 VPN으로. Unit 13의 고객용 한결봇은 **별도 공개 주소(VIP)와 서버 풀**로 새로 연다.
- 원고의 실제 공인 IP(3.3.3.3, 9.9.9.9 등)는 아래 장부 주소로 바꾼다. 6G 전망은 뺀다. 실제 제품·회사명은 일반명으로(예: "오픈소스 IDS 규칙 형식").
- ARP 방식 NAC는 원리 한 문단까지만. 절차·도구 없음.
- Unit 15 마지막 Page는 Lesson 상자 대신 **심화편 전체 생각법 회고 상자 하나**.
- 퀴즈 ID는 새 위치 기준 `u{unit}-l{lesson}-p{page}-q{n}` (예: `u11-l03-p02-q01`).
- 근거 없는 수치(미러링 누락률, 회선 가격 등)는 빼거나 "가정"이라고 밝힌다.

### 기술 정확성 주의 (Luna 검토)

- 프록시는 **자신이 중계·종료하는 연결에서만** 애플리케이션 내용을 해석한다. HTTPS 내용은 회사 CA 설치와 TLS 검사 설정이 있을 때만 보인다.
- 포트 번호는 관례일 뿐 프로토콜·암호화 여부를 보증하지 않는다(80번 ≠ 반드시 평문 HTTP).
- 포트 포워딩은 "외부 포트로 온 연결을 지정한 내부 주소·포트로 변환·전달하는 규칙". 실제 접속 허용은 방화벽·필터 정책과 별개로 확인한다. UPnP도 매핑 요청과 실제 도달 가능 여부를 구별한다.
- 시그니처 검사의 범위는 센서 위치와 TLS 종료 위치에 달렸다.

## 독자

- 기본편 Unit 1~10(IP, 포트, TCP/UDP, DNS, HTTP, 웹 서비스 구조)을 마친 초보자.
- 네트워크 전공자가 아니라, 회사에서 AI를 도입하거나 쓰는 실무자. 개발자일 수도 아닐 수도 있다.
- 목표는 장비 이름 암기가 아니라 **"막혔을 때 어디를 의심하고, 무엇을 바꾸면 어떤 대가가 있는지"를 스스로 생각하는 힘**.

## 관통 시나리오 — 「한결디자인」의 사내 AI 도입

직원 40명 인테리어 설계 회사 **한결디자인**이 업무에 AI를 들인다. 등장인물은 세 명으로 고정한다.

| 인물 | 역할 | 주로 겪는 문제 |
| --- | --- | --- |
| **지우** | 신입 IT·보안 담당(독자의 대리인). 네트워크 기본편 수준 | 문제를 받아서 원인을 추적한다 |
| **박 팀장** | 디자인팀장. AI를 제일 적극적으로 쓴다 | "왜 안 돼요?" 요청, 재택근무 |
| **서 이사** | 경영진. 비용·보안·고객 신뢰를 따진다 | "그거 안전해요? 얼마 들어요?" |

AI 도입은 다음 순서로 커진다. Unit마다 그 시점의 문제가 Lesson을 연다.

| Unit | 이야기 시점 | 대표 문제 예 (설계 agent가 다듬는다) |
| --- | --- | --- |
| 11 장치 배치·프록시 | 직원들이 외부 AI 서비스를 쓰기 시작 | 회사 PC에서만 AI 사이트가 안 열림 / 고객 도면·개인정보를 AI에 붙여넣는 걱정 / 누가 어떤 AI를 쓰는지 모름(숨은 AI 사용) / AI 앱이 실제로 뭘 보내는지 궁금함 / 사내 AI 서버를 외부 공격에서 보호 |
| 12 공유기·NAT | 지우가 GPU PC에 사내용 AI 모델 서버를 직접 띄움 | 사무실에선 되는데 밖에서 접속 안 됨 / 포트 포워딩으로 열기 / 프로그램이 몰래 포트를 연 UPnP 위험 |
| 13 부하 분산 | 사내 AI 챗봇 「한결봇」을 고객 상담에 공개 | 사용자가 몰려 느려짐 / 모델 로딩 중인 서버로 요청이 감 / 장비 한 대 고장에 전체 중단 / 해외 고객·지사 응답 지연 |
| 14 VPN | 재택·지사에서 사내 AI(사내 문서 연동) 사용 | 집에서 사내 AI 서버 접속 / 지사와 본사 연결 / VPN으로 지역 제한을 우회할 때의 문제 |
| 15 보안 솔루션 | AI 도입 후 보안 점검 | 개인 노트북이 사내망에 붙음 / 방화벽 규칙 / AI 서버를 노린 공격 탐지 / 여러 장비 로그를 모아 이상 징후 찾기 |

- 시나리오는 **도입부의 장식이 아니라 설명의 재료**다. 개념을 설명할 때 한결디자인의 실제 주소·장비·요청으로 예를 든다.
- 특정 실제 AI 제품명은 꼭 필요할 때만 일반명으로 쓴다("외부 AI 채팅 서비스", "AI API").
- 사실과 다른 가짜 수치·제품 동작을 지어내지 않는다. 예시 IP는 문서용 범위(192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24)와 사설 범위를 쓴다.

## 컴퓨터적 사고 — 무엇을 짚나

AX에서 필요한 사고는 "AI에게 일을 맡기든 사람이 고치든, 문제를 **쪼개고, 공통 구조를 보고, 필요한 것만 남기고, 순서대로 확인**하는 것"이다. 이 과정에서 쓸 생각법은 아래 다섯 가지로 고정해 반복한다(이름을 바꾸지 않는다).

| 생각법 | 네트워크에서의 모습 |
| --- | --- |
| 🧩 **쪼개기**(분해) | "안 열린다"를 DNS·경로·포트·정책 중 어디서 막혔는지로 나눈다 |
| 🔁 **같은 모양 찾기**(패턴) | 포워드 프록시와 리버스 프록시, NAT와 L4가 같은 구조의 변형임을 본다 |
| 🗺️ **필요한 것만 남기기**(추상화) | 장비 이름 대신 "경로 안에 있나/밖에 있나/대신 연결하나"로 본다 |
| 📋 **순서대로 확인하기**(절차) | 가까운 곳부터, 한 번에 하나만 바꾸며 확인한다 |
| ⚖️ **대가 따지기**(트레이드오프) | 막으면 안전하지만 느려지고, 열면 편하지만 노출된다 |

- 각 Page 본문은 **문제(상황) → 원인(왜 그런가, 개념 설명은 여기서 충분히) → 해결(과 그 대가)** 순서로 흐른다. 소제목으로 「문제」「원인」을 기계적으로 박지 말고 문단 흐름으로 보여 준다.
- Lesson 마지막 Page 끝에 「🧠 이번에 쓴 생각법」 상자: 이 Lesson에서 실제 쓴 생각법 2~3개를, 이 Lesson의 장면에 붙여 한 줄씩.

## 제목 기준

- **Lesson 제목**: 독자가 겪을 문제나 궁금증. 개념 이름은 뒤에 붙일 수 있다.
  - ✗ 「인라인 구조와 트래픽 처리」 → ✓ 「길목을 지키는 장치: 인라인」 / 「회사 PC에서만 AI가 안 열리는 이유」
- **Page 제목**: 그 Page가 답하는 한 가지 질문이나 장면. 20자 안팎. 물음표·구어체 가능. 같은 Lesson 안에서 형식을 통일한다.
  - ✗ 「Interface와 안쪽·바깥쪽」 → ✓ 「방화벽은 어느 쪽이 안인지 어떻게 알까?」
- 기술 용어는 제목에서 빼지 않아도 되지만, 제목만 읽어도 "아, 이게 궁금했지" 싶어야 한다.

## Page 본문 기준 (집필 단계)

- 혼공네트 문체: 친근한 설명체(~다/~자), 한 문단 3~5문장, 비유 먼저 정확한 설명 뒤.
- Page당 본문 약 900~1,500자. 짧은 요약으로 끝내지 않는다. 비교는 표가 낫다면 표로.
- 첫 Page 첫 문단은 **이 Lesson을 왜 배우는지**를 한결디자인 장면으로 연다.
- 출처: 기존 원고(oeweo 원천 강의), 「혼자 공부하는 네트워크」(혼공네트) 해당 절. 실제 참고한 문서·절·앵커를 기록한다. 원문을 길게 옮기지 않는다.
- 기존 원고의 기술 내용은 버리지 않는다. 새 Page에 흡수하거나, 뺐다면 이유를 대응표에 적는다.
- 용어 하이라이트·이모지·glossary 확장은 이번 범위가 아니다. 기존 표기를 망가뜨리지 않는다.

## 퀴즈 기준

`docs/QUIZ_AUTHORING_RULES.md`를 따른다. 추가로:

- ① 개념 확인(easy): 해당 개념 문단 바로 뒤.
