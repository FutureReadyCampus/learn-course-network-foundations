## 반드시 고칠 것

1. **`07-리버스-프록시와-서버-앞단/lesson.md` / 「손님 대리인과 서버 경비는 무엇이 다를까?」, 「암호는 어디서 풀어야 할까?」, 「포워드와 리버스는 같은 모양일까?」**
   **문제:** 주소 장부와 원고 안에서 공개 주소가 다르다. 장부는 고객용 VIP를 `203.0.113.10:443`으로 정했는데, 본문과 퀴즈는 `198.51.100.25`를 리버스 프록시 주소로 쓴다. `198.51.100.25`는 장부상 본사 게이트웨이 주소다.
   **수정안:** `ai.hangyeol.example`의 DNS 응답과 고객 연결 대상을 `203.0.113.10:443`으로 통일한다. Lesson 11-2~11-5의 회사 출구 주소 `198.51.100.25`는 본사 게이트웨이/NAT 주소로 유지한다. 이에 따라 `u11-l07-p01-q02`의 DNS 결과와 연결 상대도 함께 고친다.

2. **`07-리버스-프록시와-서버-앞단/lesson.md` / 「손님 대리인과 서버 경비는 무엇이 다를까?」, 「암호는 어디서 풀어야 할까?」**
   **문제:** 이 Lesson은 Unit 12에서 띄울 사내 AI 서버를 `192.168.10.50:8080`으로 쓰지만, Unit 11 blueprint의 공통 예시값은 계획 중인 서버 `192.168.10.60`으로 적었다. 장부에는 별도로 `.50:8080`이 사내 AI 서버로 지정되어 있어 blueprint 안에서도 충돌한다.
   **수정안:** 실제 주소로 사용할 서버 주소를 하나로 확정해 blueprint와 본문·퀴즈 전체에 적용한다. 이미 본문·퀴즈와 통일 주소 장부에 반복 등장하는 `.50:8080`을 유지한다면, blueprint의 “계획 중 `192.168.10.60`”을 `.50:8080`으로 고친다.

3. **`03-경로-밖-관찰과-dpi/lesson.md` / 「HTTPS 시대에 센서는 무엇을 볼까?」 및 「미러링을 켰는데 기록이 비는 이유는?」**
   **문제:** 다섯 번째 고민의 요약과 퀴즈가 SNI를 이용해 센서가 `ai-chat.example` 같은 서비스 이름을 알아낼 수 있다고 읽힌다. 하지만 SNI는 TLS 연결에서 서버 이름을 제공하는 확장이고, 암호화되지 않은 SNI가 항상 관찰된다고 단정할 수 없다. 본문에서 이 한계를 설명하지 않으면 탐지 능력을 과장하게 된다.
   **수정안:** “SNI가 보이는 연결에서는 서버 이름을 단서로 삼을 수 있지만, 항상 보이는 것은 아니다. 센서는 목적지 IP·시각·전송량 등도 함께 보고, 이 정보만으로 요청 내용까지 알 수는 없다”는 설명을 넣는다. 이에 맞춰 `u11-l03-p05-q02`의 “SNI `ai-chat.example`”도 관찰 조건이 명시된 상황으로 바꾼다.

4. **`01-장치가-트래픽을-다루는-세-가지-구조/lesson.md` / 「다섯 고민을 세 갈래로 나눌 수 있을까?」 및 `07-리버스-프록시와-서버-앞단/lesson.md` / 「포워드와 리버스는 같은 모양일까?」**
   **문제:** 11-1의 도입은 다섯 고민을 “세 갈래”로 정리한다고 예고하지만, 마지막 요약표에서 **누가 어떤 AI를 쓰는지 모른다**는 고민은 빠져 있다. 11-7의 표에는 해당 고민이 경로 밖 센서에 배정되어 있지만, 그 Lesson에서 센서의 관찰 한계와 SNI 조건을 충분히 전제하지 않는다.
   **수정안:** 11-1 p1에서 다섯 고민 각각을 세 구조 중 어디서 다룰지 미리 연결하고, 11-7 요약표의 누락 항목을 포함한다. 센서가 알 수 있는 범위는 “목적지·시각·양 및 조건부 서버 이름”으로 제한해 적는다.

## 고치면 좋은 것

- **Page 첫머리의 질문과 앞 문단의 반복:** 여러 Page가 바로 앞 Page에서 이미 소개한 문제를 다시 길게 설명한다. 특히 11-2 「AI 요청은 어떤 장치를 거쳐 나갈까?」는 Lesson 도입 장면과 겹친다. 첫 문단은 해당 Page에서 해결할 새 질문으로 바로 들어가면 흐름이 가벼워진다.
- **11-1 p1의 두 분류 기준:** “어디에 붙나”는 세 구조를 구분하지만, “패킷과 Stream 중 무엇을 보나”는 각 구조의 정의와 항상 일대일로 대응하지 않는다. 예컨대 인라인 장치도 애플리케이션 계층을 해석할 수 있다. 구조 분류 기준과 흔한 처리 단위를 별도 문장으로 설명하면 더 정확하다.
- **용어가 먼저 나오는 부분:** TAP, Tapping Point, Stream, SPOF, DPI, TLS 종단, 오탐·미탐 등이 정의나 익숙한 예보다 먼저 등장하는 곳이 있다. 처음 나오는 문장에서 쉬운 풀이를 먼저 붙이는 편이 초보자에게 안전하다.
- **`u11-l03-p07-q01` 계산 문항:** 1Gbps를 바이트로 바꾸는 개념 확인 자체는 유효하지만, 문제의 핵심이 Unit의 센서 저장량이라면 가정한 회선 사용률과 저장 단위(십진 TB/이진 TiB), 패킷·파일시스템 오버헤드를 구분해 근사치임을 분명히 할 필요가 있다.
- **11-7 끝부분의 다리 문단:** Module 3 자동화 예고와 Unit 12 예고가 한 문단에 함께 들어가 Unit 11의 마무리가 분산된다. Unit 12로 이어지는 장면을 먼저 닫고 Module 예고를 별도 짧은 문장으로 두면 결말이 또렷해진다.
- **문체 반복:** “지우는 설계도에 … 적는다”, “가장 알맞은 것은 무엇인가요?”가 퀴즈와 본문에서 반복된다. 의미는 분명하지만 일부 장면에서는 기록·결정·확인 행동을 더 구체적으로 바꿀 수 있다.

## 퀴즈 문제 목록

- **`u11-l01-p01-q02` / 중복·본문 재탕:** 본문과 바로 전 Lesson 첫 페이지가 이미 회계팀의 “기록은 남기되 업무를 멈추지 말라” 상황으로 Out of path를 설명한다.
  **수정안:** 새 장면으로 바꾼다. 예: “감사팀이 AI 사용량을 집계하되 장애 원인을 분석할 때는 요청 본문을 볼 필요가 없다”를 제시하고, 복사 관찰이 적절한 이유와 차단 불가라는 한계를 함께 판단하게 한다.

- **`u11-l03-p05-q02` / 조건 누락:** SNI와 서비스명을 확정적으로 결합해 센서가 항상 그 이름을 본다는 인상을 준다.
  **수정안:** “보고서에 SNI 값이 기록됐고 해당 연결에서 이름이 관찰됐다고 가정한다”는 조건을 발문에 추가하고, 그 정보만으로 업로드한 파일의 내용은 알 수 없다는 선택지를 정답으로 둔다.

- **`u11-l05-p07-q02` / 본문 재탕:** 본문에서 이미 계약서 속 고객 정보 유출 방지와 최소 수집을 설명한 뒤, 같은 목표를 그대로 물어 정답이 쉽게 노출된다.
  **수정안:** 새 업무 상황(예: AI 번역 도구에 개인정보가 입력되는지 우려)을 주고, TLS 검사·기록 범위·예외·고지 중 필요한 조합을 고르게 한다.

- **`u11-l06-p04-q02` / 정답 단서 과다:** 발문에서 루트 인증서 설치 후 브라우저만 되고 플러그인은 원래 설정으로 복구하면 된다고 이미 알려줘, 인증서 고정 가능성을 거의 직접 제시한다.
  **수정안:** 증상만 제시하고, 인증서 신뢰 저장소 사용 여부를 확인할지, 직접 연결과 프록시 연결 결과를 비교할지 진단 순서를 고르게 한다.

- **`u11-l07-p01-q02` / 주소 충돌:** `198.51.100.25`를 고객용 리버스 프록시 주소로 사용한다. 통일 주소 장부에 맞춰 VIP `203.0.113.10`으로 바꾸고, 본문도 함께 정합성을 맞춘다.

- **`u11-l02-p06-q02` / 오답 품질:** “목적지 포트 443은 모두 Drop, 단 특정 주소 허용” 규칙이 다른 HTTPS 사이트를 끊는다는 정답 구조는 타당하지만, 규칙 자체가 지나치게 거칠어 오답이 쉽게 배제된다.
  **수정안:** 후보 규칙들을 모두 실제 운영에서 선택할 법한 대안으로 구성하고, 목적지 주소만으로 서비스 식별이 불완전할 수 있다는 한계까지 판단하게 한다.

## 잘된 점

- 다섯 고민을 장치 이름 대신 경로 위치·처리 방식으로 연결해 Unit 전체의 학습 목적이 분명하다.
- HTTPS 검사, 포트 번호, 경로 밖 센서의 차단 한계를 여러 Lesson에서 일관되게 다룬다.
- 많은 퀴즈가 새 업무 상황을 사용하고, 정답 피드백에 판단 기준과 생각법을 연결한다.
